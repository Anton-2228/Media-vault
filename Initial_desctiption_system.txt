СИСТЕМА ДЛЯ СОХРАНЕНИЯ ВСЕГО ЧЕГО МОЖНО В ЦЕНТРАЛИЗОВАННОМ ВИДЕ



ИДЕЯ:
Идея в том, чтобы автоматически сохранять медиа информацию из разных источников(телеграмм, телефон и тд) в централизованное хранилище.



МИКРОСЕРВИСЫ, ИЗ КОТОРЫХ СОСТОИТ ПРОЕКТ:
1) Основное файловое хранилище.
Хранение файлов будет осуществляться в seafile, однако код должен поддерживать безболезненный переезд на любое другое файловое хранилище(взаимодействие с файловым хранилищем должно идти строго через наш интерфейс).
Файловое хранилище должно хранить всю информацию, необходимаю для работы системы и для сохранения целостности и консистентности данных.
С основным файловым хранилищем взаимодействие идет только через сервис-обертку. Никто больше не имеет прямого доступа к основному файловому хранилищу.

2) База данных.
Хранение информации, необходимой для работы проекта, но не связанной напрямую с самими файлами должно осуществляться в PostgreSQL.
С базой данных взаимодействие идет только через сервис-обертку. Никто больше не имеет прямого доступа к базе знаний.

3) Сервис-обертка над базой знаний.
Сервис должен быть оберткой над базой знаний.
Написан должен быть на python. Взаимодействие с PostgreSQL должно осуществляться через SQLAlchemy.
Для работы с сетью должен выступать FastAPI.
Собственной авторизации у сервиса-обертки нет: она не проверяет, какой внутренний сервис к ней обращается, и не ограничивает, к каким данным он имеет доступ (см. раздел "ДОВЕРИЕ МЕЖДУ ВНУТРЕННИМИ СЕРВИСАМИ").

4) Сервис обработки файлов.
Воркер, который обрабатывает файлы внутри системы. С сервисами-пользователями он не взаимодействует и запросов от них не получает.
Задания на обработку он получает через кафку от сервиса доступа к файлам. В задании приходит id операции, всю конкретику (что за файл, какой файл подменить, какую метаинформацию изменить) он берет из операции в postgres.
Получив задание о загруженном файле, он обрабатывает файл, если необходимо, перемещает его из места временного хранения в нужную директорию и создает файл с метаинформацией о нем. Подмену файла и изменение метаинформации файла также выполняет он по заданию.
Каждое внесенное изменение он фиксирует в операции, а результат выполнения задания (успех или ошибка) через кафку сообщает сервису доступа к файлам.
С файловым хранилищем и базой данных работает через сервис-обертку. После каждого изменения в файловом хранилище пишет сообщение об этом в топик сервиса подписок.
Написан должен быть на python.

5) Сервис авторизации.
Отвечает за прием заявок на регистрацию сервисов-пользователей, хранение одобренных сервисов-пользователей, выдачу bearer-token-ов и их проверку. Сервис обработки файлов этой логикой не занимается.
Мастер-ключа в системе нет. Регистрация идет через заявку: подать заявку может любой сервис-пользователь, но учетные данные он получает только после того, как администратор одобрит заявку в сервисе администрирования (см. раздел "АВТОРИЗАЦИЯ").
Предоставляет сервису администрирования внутренний API: вход администратора, список заявок, одобрение и отклонение заявки, блокировка сервиса-пользователя, перевыпуск его секрета. Вся логика рассмотрения заявок живет здесь, сервис администрирования только отображает ее.
Данные о заявках, зарегистрированных сервисах-пользователях и администраторах хранит в PostgreSQL через сервис-обертку. Секреты сервисов-пользователей и пароли администраторов хранит только в виде хеша.
Написан должен быть на python.

6) Сервис доступа к файлам.
Все взаимодействие сервисов-пользователей с файлами идет через него: запросы на загрузку, подмену и скачивание файла, сообщения о загруженных файлах, запросы и изменение метаинформации gateway направляет в сервис доступа к файлам.
Проверяет можно ли выполнить запрошенное действие с файлом (см. раздел "ПОЛИТИКА ДОСТУПА К ФАЙЛАМ") и выдает одноразовые токены с ttl на загрузку и скачивание файлов.
Метаинформацию о файлах по запросу сервиса-пользователя отдает он же.
На каждое действие сервиса-пользователя с файловым хранилищем он создает в postgres операцию и ведет ее до завершения или отката (см. раздел "ОПЕРАЦИИ"). Сервису-пользователю он отдает id операции, и дальше сервис-пользователь общается с ним только по id операции.
Сам файлы он не обрабатывает: задания на обработку загруженного файла, подмену файла и изменение метаинформации он через кафку передает сервису обработки файлов, указывая id операции.
Если действие разрешено, сервис доступа к файлам фиксирует состояние файла (резервирует в postgres имя файла) и выдает одноразовый токен, привязанный к операции.
Одноразовый токен проверяет тот же сервис, который его выдает: gateway, получив от сервиса-пользователя запрос на загрузку или скачивание файла, делает запрос на сервис доступа к файлам для проверки одноразового токена и только после этого пропускает запрос в сервис-обертку. В ответ на проверку сервис доступа к файлам отдает gateway все параметры действия из операции: тип действия (загрузка или скачивание), путь в файловом хранилище, id операции. Gateway выполняет запрос в сервис-обертку только с этими параметрами (см. раздел "ОПЕРАЦИИ").
Данные хранит в PostgreSQL через сервис-обертку.
Написан должен быть на python.

7) Сервис подписок.
Используется для реализации подписок на изменения в файловом хранилище.
Принимает подписки от сервисов-пользователей, получает события об изменениях в файловом хранилище, формирует уведомления для подписанных сервисов-пользователей и через кафку отправляет их в сервис-нотифайер.

8) Сервис-нотифайер.
Занимается только отправкой уведомлений сервисам-пользователям. Уведомления получает через кафку от сервиса подписок и отправляет их сервисам-пользователям через gateway по web socket (см. раздел "ДОСТАВКА УВЕДОМЛЕНИЙ"). Сам соединений с сервисами-пользователями не держит: просит gateway доставить уведомление сервису-пользователю по его идентификатору и получает ответ, доставлено или нет.
В сервисе-нотифайере должна быть таблица с уведомлениями и политикой ретраев.
Политика ретраев должна быть экспоненциально затухающей: каждый следующий ретрай выполняется через в 2 раза большее время, чем предыдущий.

9) Kafka.
Кафка используется только для взаимодействия между внутренними сервисами системы. Сервисы-пользователи с кафкой не взаимодействуют: все свои запросы они отправляют через gateway.
Через кафку сервис доступа к файлам передает задания сервису обработки файлов, сервис обработки файлов возвращает ему результаты выполнения заданий и передает события об изменениях сервису подписок, а сервис подписок передает уведомления сервису-нотифайеру.

10) Gateway.
Единая точка входа для сервисов-пользователей. Сервис-пользователь не обращается к внутренним сервисам напрямую: все его запросы приходят в gateway, который перенаправляет их в нужный сервис (сервис авторизации, сервис доступа к файлам, сервис подписок, сервис-обертку). Одноразовые токены на загрузку и скачивание файлов gateway проверяет запросом в сервис доступа к файлам. Из запроса сервиса-пользователя на загрузку или скачивание gateway берет только одноразовый токен и тело файла. Путь, тип действия и все остальные параметры он получает от сервиса доступа к файлам из операции и подставляет в запрос к сервису-обертке сам: ничего из того, что сервис-пользователь прислал в запросе кроме токена и тела файла, в сервис-обертку не попадает.
В обратную сторону то же самое: уведомления от сервиса-нотифайера идут сервисам-пользователям через gateway. Для этого gateway держит web socket соединения с сервисами-пользователями: сервис-пользователь сам открывает соединение к gateway, предъявив bearer-token, gateway проверяет его в сервисе авторизации и запоминает, какому сервису-пользователю принадлежит соединение (см. раздел "ДОСТАВКА УВЕДОМЛЕНИЙ").
Когда я пишу, что сервис-пользователь обращается к какому-то внутреннему сервису, подразумевается, что он делает это через gateway.
Сам gateway bearer-token не проверяет: на каждый запрос сервиса-пользователя он делает запрос в сервис авторизации, и тот проверяет токен. Запросы, токен которых сервис авторизации не подтвердил, gateway дальше не пропускает. Исключение - подача заявки на регистрацию, запрос статуса заявки и запрос bearer-token-а. Эти запросы доступны без токена, поэтому gateway ограничивает их частоту по адресу отправителя. Gateway же терминирует TLS и применяет лимиты на частоту запросов и размер тела (см. раздел "TLS И ЛИМИТЫ GATEWAY").
Сервис администрирования через gateway не доступен: это внутренний сервис для администратора, а не для сервисов-пользователей.

11) Множество регистрируемых сервисов-пользователей.
Сервисы-пользователи должны подать заявку на регистрацию, дождаться ее одобрения администратором, получить свои учетные данные, после чего в своем life circle отправлять медиа в систему и/или получать медиа из нее.
Написаны могут быть на чем угодно.

12) Сервис администрирования.
Frontend-сервис с веб-интерфейсом для администратора системы. Используется для приема заявок на регистрацию сервисов-пользователей: администратор видит список заявок с их названием, описанием и датой подачи, одобряет или отклоняет их с указанием причины. Там же администратор видит список зарегистрированных сервисов-пользователей, может заблокировать любой из них и перевыпустить его секрет.
Собственной бизнес-логики не содержит: все действия выполняет запросами во внутренний API сервиса авторизации. Напрямую к базе данных и к сервису-обертке не обращается.
Вход в интерфейс только по учетной записи администратора. Учетные данные администратора проверяет сервис авторизации. Первая учетная запись администратора создается при развертывании системы. Доступен только по TLS, попытки входа ограничены: не более 5 неудачных попыток в минуту с одного адреса, после чего адрес блокируется на 15 минут.
Наружу не публикуется и через gateway не доступен: доступ к нему есть только у администратора.



АВТОРИЗАЦИЯ:
За авторизацию отвечает отдельный сервис авторизации. Мастер-ключа в системе нет: у каждого сервиса-пользователя свой секрет, который он получает после одобрения заявки администратором.
Регистрация идет через заявку с ручным одобрением:
1) Сервис-пользователь подает заявку на регистрацию в сервис авторизации, передавая свое название и описание (кто он, какие источники будет присылать). Подать заявку может любой: bearer-token для этого запроса не нужен. В ответ сервис авторизации отдает id заявки. Id заявки - случайное непредсказуемое значение, его знает только подавший заявку сервис-пользователь, и по нему он потом забирает учетные данные;
2) Заявка попадает в состояние "ожидает" и появляется в сервисе администрирования. Администратор одобряет или отклоняет ее;
3) Сервис-пользователь периодически запрашивает статус заявки по ее id. Пока заявка не рассмотрена, он получает статус "ожидает". Если заявка отклонена, он получает статус "отклонена" и причину;
4) Если заявка одобрена, сервис авторизации при первом же запросе статуса после одобрения отдает сервису-пользователю его уникальный идентификатор и секрет. Секрет выдается ровно один раз: после выдачи заявка переходит в состояние "выдана", и повторный запрос статуса секрет не возвращает. В открытом виде секрет нигде не хранится, сервис авторизации хранит только его хеш. Если сервис-пользователь потерял секрет, администратор перевыпускает его через сервис администрирования, и новый секрет забирается тем же способом;
5) Дальше сервис-пользователь запрашивает bearer-token у сервиса авторизации, передавая свой идентификатор и секрет. После протухания сервис-пользователь перезапрашивает bearer-token.
Проверяет bearer-token тот же сервис, который его выдает, - сервис авторизации. Gateway, получив запрос от сервиса-пользователя, делает запрос на сервис авторизации для проверки токена. Внутренние сервисы получают уже проверенные запросы.
Администратор может заблокировать сервис-пользователь через сервис администрирования: его bearer-token-ы перестают проходить проверку, новые не выдаются.
Одноразовые токены на загрузку и скачивание файлов к сервису авторизации не относятся: их выдает и проверяет сервис доступа к файлам.



ОПЕРАЦИИ:
Взаимодействие сервиса-пользователя с файловым хранилищем должно быть транзакционным и атомарным. Реализуется это сагой.
Для каждой операции с файловым хранилищем (загрузка файла, подмена файла, изменение метаинформации, скачивание файла) в postgres должна создаваться операция (operation).
Создание операции инициирует сервис-пользователь. При создании он один раз сообщает всю конкретику: что это за операция, над каким файлом, с какой метаинформацией, из какого источника и тд. В ответ он получает id операции.
Дальше при общении с системой сервис-пользователь сообщает только id операции, а не ее конкретику. Изменить конкретику уже созданной операции нельзя: например нельзя запросить подмену одного файла, а потом сообщить id другого.
Одноразовые токены выдаются в рамках операции и привязаны к ней.
Операция - единственный источник всех параметров действия. Все, что нужно для выполнения шага (тип действия, путь во временном хранилище, конечный путь, id подменяемого файла, метаинформация, источник, сохранять ли имя), берется только из операции и никогда из запроса сервиса-пользователя или из сообщения в кафке. Это касается всех участников: gateway при загрузке и скачивании получает путь и тип действия от сервиса доступа к файлам из операции, сервис доступа к файлам при запросах по id операции берет конкретику из операции, сервис обработки файлов получает в задании только id операции и всю конкретику читает из операции. Параметры, присланные сервисом-пользователем после создания операции, игнорируются, а если они противоречат операции (например, другой путь), запрос отклоняется.
Операция фиксирует каждое изменение, которое было сделано в ходе ее выполнения (резервирование имени файла, загрузка файла в место временного хранения, перемещение файла, подмена файла, создание или изменение файла с метаинформацией).
Если на каком-то шаге произошла ошибка или сервис-пользователь не завершил операцию за отведенное время, то все уже зафиксированные изменения должны быть откачены в обратном порядке: файловое хранилище и postgres должны вернуться в состояние до начала операции.
Операция либо выполняется целиком, либо не оставляет после себя никаких изменений.
Ведет операции сервис доступа к файлам. Сервис обработки файлов выполняет свои шаги операции и сообщает ему результат.
Сообщение об изменении в топик сервиса подписок пишется только после успешного завершения операции.



ОТПРАВКА ФАЙЛОВ СЕРВИСОМ-ПОЛЬЗОВАТЕЛЕМ В ФАЙЛОВОЕ ХРАНИЛИЩЕ:
Обшая последовательная схема:
Когда я пишу, что какой-то сервис пишет файл в файловое хранилище, подразумевается, что он делает это через сервис-обертку этого файлового хранилища.
1) Сервис-пользователь, согласно своей внутренней логике, получает файл, который нужно сохранить в файловое хранилище;
2) Сервис-пользователь отправляет всю метаинформацию, касающуюся файла, запросом в сервис доступа к файлам;
3) Сервис доступа к файлам получает метаинформацию, создает операцию и проверяет можно ли загрузить файл в файловое хранилище;
4) Если загрузить файл нельзя, то сервис доступа к файлам завершает операцию с ошибкой и сообщает об этом сервису-пользователю в ответе на запрос;
5) Если загрузить файл можно, то сервис доступа к файлам фиксирует состояние этого файла, чтобы никто другой не мог каким-то образом помешать дальнейшей загрузке файла в файловое хранилище(резервирует в postgres имя файла, чтобы другой сервис-пользователь не мог его занять). Путь во временном хранилище, по которому будет загружен файл, он записывает в операцию. После отдает сервису-пользователю в ответе на запрос id операции, одноразовый токен с ttl и url gateway, по которому файл необходимо загрузить. Этот токен должен давать возможность загрузить файл только по пути, записанному в операции;
6) Сервис-пользователь отправляет файл по этому url в gateway, передавая только одноразовый токен и тело файла. Gateway проверяет токен в сервисе доступа к файлам, получает от него из операции путь во временном хранилище и через сервис-обертку файлового хранилища сохраняет файл по этому пути (в seafile это специальная директория, в S3 это будет просто специальный подпуть). Путь от сервиса-пользователя не принимается;
7) Сервис-пользователь запросом в сервис доступа к файлам сообщает ему, что файл загружен, передавая только id операции;
8) Сервис доступа к файлам через кафку передает задание на обработку файла сервису обработки файлов, указывая id операции;
9) Сервис обработки файлов обрабатывает файл, если необходимо, перемещает его в нужную директорию, а также создает файл с метаинформацией о файле. Каждое изменение он фиксирует в операции;
10) Сервис обработки файлов через кафку сообщает результат сервису доступа к файлам. При успехе операция завершается, при ошибке все изменения, сделанные в рамках операции, откатываются;

Когда сервис-пользователь отправляет медиа он должен также отправлять информацию об источнике этой медиа. Источник может быть вложенным. Передавать необходимо списком, где каждый следующий элемент это подкаталог. Файлы в файловом хранилище должны группироваться соответственно источнику. Если источник вложенный, то должно формироваться дерево каталогов.

Вместе с самим файлом в файловое хранилище должен сохраняться json файл с метаинформацией о нем.
Этот json файл необходимо сохранять по тому же пути, но в другую директорию на верхнем уровне.
Например если файл сохранен по пути "<путь_к_корневой_директории_проекта>/file_storage/youtube/channel_name/video_1.mp4", то json файл с метаинформацией должен быть сохранен в "<путь_к_корневой_директории_проекта>/metadata/youtube/channel_name/video_1.json"
Сервис обработки файлов должен сохранять туда:
1) Уникальный id файла(UUID);
2) Название файла;
3) Расширение файла;
4) Вес файла;
5) Дату и время добавления файла;
6) Сервис-пользователь, приславший файл;
7) Источник, откуда сервис-пользователь взял файл;
8) Возможно ещё какие-то поля;

Сервис-пользователь при отправке файла должен иметь возможность добавить свою метаинформацию о файле. Подаваться должно в формате json, который будет 1 в 1 добавлен к метаинформации о файле. В случае коллизий имен с системными ключами необходимо не сохранить файл и сообщить об этом сервису-пользователю.

Сервис-пользователь при отправке файла должен указывать нужно ли сохранять имя файла или нет. Если имя сохранять не нужно, то сервис обработки файлов должен переименовать файл при помощи UUID. Если имя нужно сохранять, но в файловом хранилище файл с таким именем по такому пути уже существует, то необходимо не сохранять файл и сообщить об этом сервису-пользователю.



ПОЛУЧЕНИЕ ФАЙЛОВ СЕРВИСОМ-ПОЛЬЗОВАТЕЛЕМ ОТ ФАЙЛОВОГО ХРАНИЛИЩА
Должно быть 2 пути:
1) Запрос метаинформации по файлу/файлам;
2) Запрос самого файла;

Общая последовательная схема запроса метаинформации по файлу/файлам:
1) Сервис-пользователь запрашивает у сервиса доступа к файлам метаинформацию по id файла/файлов или фильтрам;
2) Сервис доступа к файлам отправляет в ответе на запрос всю метаинформацию по запрашиваемому файлу/файлам;

Общая последовательная схема запроса файла/файлов:
Когда я пишу, что какой-то сервис пишет файл в файловое хранилище, подразумевается, что он делает это через сервис-обертку этого файлового хранилища.
1) Сервис-пользователь запрашивает у сервиса доступа к файлам файл/файлы по его/их id;
2) Сервис доступа к файлам создает операцию и проверяет можно ли скачать файл/файлы (файлы существуют, см. раздел "ПОЛИТИКА ДОСТУПА К ФАЙЛАМ"). Если можно, то в ответе на запрос дает сервису-пользователю id операции, одноразовый токен с ttl на каждый запрашиваемый файл и url/url-ы, по которому надо скачать файл/файлы. Токен должен позволять скачать файл только по конкретному пути;
3) Сервис-пользователь скачивает файлы по этим url в gateway, передавая только одноразовый токен. Gateway проверяет токен в сервисе доступа к файлам, получает от него из операции путь файла в файловом хранилище и отдает файл по этому пути через сервис-обертку файлового хранилища. Путь от сервиса-пользователя не принимается;

Должны быть фильтры:
1) По сервису-пользователю, который добавил/изменил файл;
2) По источнику файла(если у указанного источника есть подисточники, то возвращать нужно рекурсивно все файлы из подисточников);
2) По типу файла (png, mp4, pdf и т.д.);
3) Возможно ещё какие-то фильтры;



РЕДАКТИРОВАНИЕ ФАЙЛОВ СЕРВИСОМ-ПОЛЬЗОВАТЕЛЕМ В ФАЙЛОВОМ ХРАНИЛИЩЕ:
Сервис-пользователь должен иметь возможность редактировать файлы, уже загруженные на файловый сервер.
Должна быть возможность:
1) Подменить сам файл;
2) Добавить поля с метаинформацией;
3) Обновить существующие поля с метаинформацией;
4) Возможно ещё что-то;

Общая последовательная схема подмены файла такая же, что и при загрузке файла, но файл должен не просто загружаться, а подменять существующий, id которого сервис-пользователь сообщил сервису доступа к файлам при создании операции. Этот id сохраняется в операции и после ее создания измениться не может: дальше сервис-пользователь сообщает только id операции, и сервис обработки файлов берет id подменяемого файла из операции.
Изменение метаинформации файла также идет через операцию: сервис-пользователь создает операцию в сервисе доступа к файлам, тот передает задание сервису обработки файлов.



ПОДПИСКА НА ИЗМЕНЕНИЯ В ФАЙЛОВОМ ХРАНИЛИЩЕ
У сервиса-пользователя должна быть возможность подписаться на изменения в файловом хранилище.
Должна быть возможность подписаться на добавление/изменение файла в файловом хранилище.
Общая схема:
1) Сервис-пользователь через сервис подписок подписывается на определенный вид изменений в файловом хранилище. Подписаться должна быть возможность на добавление файла, перезапись файла, изменение метаинформации файла, возможно ещё что-то. Также должны быть фильтры по сервису-пользователю, который добавил файл, по источнику файла, по типу файла(jpg, mp4 и тд), возможно ещё по чему-то;
2) После того, как сервис обработки файлов внес изменение в файловое хранилище он пишет в топик сервиса подписок сообщение об этом изменении;
3) Сервис подписок по подпискам и их фильтрам определяет, каким сервисам-пользователям нужно сообщить об изменении, формирует для них уведомления и пишет их в топик сервиса-нотифайера;
4) Сервис-нотифайер сохраняет уведомления в свою таблицу и через gateway отправляет их нужным сервисам-пользователям по web socket. Если доставить уведомление не удалось (сервис-пользователь не подключен или не подтвердил получение), он повторяет отправку согласно политике ретраев, каждый раз увеличивая интервал до следующей попытки в 2 раза;



ДОСТАВКА УВЕДОМЛЕНИЙ
Уведомления доставляются сервисам-пользователям по web socket. Соединение всегда инициирует сервис-пользователь, система к сервисам-пользователям сама не подключается: никаких callback-url сервис-пользователь не сообщает и не хранит.
Общая схема:
1) Сервис-пользователь открывает web socket соединение к gateway, предъявив bearer-token. Gateway проверяет токен в сервисе авторизации и, если токен валиден, принимает соединение и запоминает, какому сервису-пользователю оно принадлежит. У одного сервиса-пользователя может быть несколько соединений (несколько экземпляров сервиса-пользователя);
2) Соединение живет не дольше bearer-token-а: по протуханию токена gateway закрывает соединение, сервис-пользователь получает новый токен и переподключается. Если сервис-пользователь заблокирован, gateway закрывает его соединения;
3) Сервис-нотифайер, получив уведомление, запросом в gateway просит доставить его сервису-пользователю по идентификатору. Gateway находит открытое соединение этого сервиса-пользователя и отправляет уведомление в него. Если соединений несколько, уведомление отправляется в одно из них;
4) Сервис-пользователь, получив уведомление, отправляет в то же соединение подтверждение с id уведомления. Уведомление считается доставленным только после подтверждения. Если у сервиса-пользователя нет открытого соединения или подтверждение не пришло за отведенное время, gateway отвечает сервису-нотифайеру, что доставить не удалось;
5) Недоставленное уведомление сервис-нотифайер повторяет согласно политике ретраев. Сервис-пользователь должен быть готов получить одно и то же уведомление повторно (если подтверждение потерялось) и отличать повторы по id уведомления.
Через web socket идут только уведомления и подтверждения их получения. Все остальные запросы сервис-пользователь отправляет обычными запросами через gateway.



TLS И ЛИМИТЫ GATEWAY
Весь трафик между сервисами-пользователями и системой идет только по TLS: и обычные запросы, и загрузка/скачивание файлов, и web socket соединения. TLS терминирует gateway, незащищенные соединения он не принимает. Сервис администрирования также доступен только по TLS. Внутри закрытой сети между внутренними сервисами TLS не используется (см. раздел "ДОВЕРИЕ МЕЖДУ ВНУТРЕННИМИ СЕРВИСАМИ").
Секрет сервиса-пользователя и bearer-token передаются только в теле запроса или в заголовке Authorization, никогда в url: url попадают в логи.

Gateway ограничивает частоту запросов. Лимиты считаются по алгоритму token bucket, при превышении gateway отвечает 429 с заголовком Retry-After и запрос дальше не пропускает. Лимиты применяются до обращения в сервис авторизации, чтобы подбор секрета не нагружал его.
Запросы без токена считаются по адресу отправителя:
1) Подача заявки на регистрацию: 5 в час с одного адреса;
2) Запрос статуса заявки: 30 в минуту с одного адреса;
3) Запрос bearer-token-а: 10 в минуту с одного адреса. Дополнительно считается по идентификатору сервиса-пользователя: после 10 неудачных попыток подряд выдача токена этому идентификатору блокируется на 15 минут независимо от адреса, о блокировке сообщается в сервис администрирования;
Запросы с токеном считаются по идентификатору сервиса-пользователя:
4) Обычные запросы (операции, метаинформация, подписки): 600 в минуту, burst до 100;
5) Загрузка и скачивание файлов: не более 10 одновременных передач на сервис-пользователя, лимита на количество нет, так как каждая передача уже привязана к одноразовому токену и операции;
6) Web socket: не более 10 открытых соединений на сервис-пользователя и не более 1 нового соединения в секунду;
Все значения лимитов задаются конфигурацией gateway и могут быть изменены без изменения кода.

Gateway ограничивает размер тела запроса:
1) Обычные запросы (создание операции, метаинформация, подписки): 1 МБ. Этого достаточно для любой пользовательской метаинформации, более крупную метаинформацию нужно хранить как отдельный файл;
2) Загрузка файла: 20 ГБ на один файл. Лимит проверяется по заголовку Content-Length до начала передачи и по фактически переданному объему во время передачи, при превышении соединение разрывается, а операция откатывается;
3) Сообщение в web socket от сервиса-пользователя (подтверждение получения): 4 КБ;
Таймаут на бездействие при загрузке и скачивании файла: 60 секунд без передачи данных, после чего соединение разрывается, а операция загрузки откатывается.

ДОВЕРИЕ МЕЖДУ ВНУТРЕННИМИ СЕРВИСАМИ
Пока что авторизации между внутренними сервисами нет. Все внутренние сервисы (gateway, сервис авторизации, сервис доступа к файлам, сервис обработки файлов, сервис подписок, сервис-нотифайер, сервис администрирования, сервис-обертка) считаются доверенными: любой из них может обратиться к любому другому внутреннему сервису, а через сервис-обертку - к любым данным в PostgreSQL и файловом хранилище. Ни сервис-обертка, ни другие внутренние сервисы не проверяют, кто к ним обращается.
Единственная граница доверия проходит между сервисами-пользователями и системой: ее держит gateway через проверку bearer-token в сервисе авторизации и проверку одноразовых токенов в сервисе доступа к файлам. Поэтому ни один внутренний сервис, кроме gateway, не должен быть доступен из внешней сети: внутренние сервисы, PostgreSQL, файловое хранилище и Kafka живут в закрытой сети, наружу публикуется только gateway. Сервис администрирования доступен только администратору из этой же закрытой сети.
Авторизация между внутренними сервисами (mTLS или сервисные токены) возможно будет добавлена позже.

ПОЛИТИКА ДОСТУПА К ФАЙЛАМ
Пока что никакой политики доступа к файлам нет. Любой зарегистрированный и не заблокированный сервис-пользователь может загружать файлы, скачивать любые файлы, подменять любые файлы и изменять метаинформацию любых файлов, в том числе загруженных другими сервисами-пользователями.
Проверка "можно ли выполнить действие" в сервисе доступа к файлам сводится к техническим условиям: сервис-пользователь прошел проверку bearer-token, файл существует (для скачивания, подмены и изменения метаинформации), имя файла не занято (для загрузки с сохранением имени), пользовательская метаинформация не конфликтует с системными ключами.
Политика доступа (владелец файла, роли, ACL) возможно будет добавлена позже. Чтобы это было безболезненно, проверка должна быть вынесена в отдельный модуль сервиса доступа к файлам с единым интерфейсом, который сейчас всегда разрешает действие, а в метаинформации файла уже сейчас должен сохраняться сервис-пользователь, который его загрузил.

ОБЩИЕ ПОЛОЖЕНИЯ СИСТЕМЫ
Каждый запрос на загрузку, скачивание, изменение и тд файлов должен логироваться в postgres. Для этого используются операции (см. раздел "ОПЕРАЦИИ").
Код должен писаться в полном соответствии принципам ООП и SOLID.
Работа с PosgreSQL должна идти через ORM. На каждую сущность в Postgres должно быть 3 сущности: DTO класс, ORM класс и класс-маппер одного в другое.
