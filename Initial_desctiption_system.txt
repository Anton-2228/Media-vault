СИСТЕМА ДЛЯ СОХРАНЕНИЯ ВСЕГО ЧЕГО МОЖНО В ЦЕНТРАЛИЗОВАННОМ ВИДЕ



ИДЕЯ:
Идея в том, чтобы автоматически сохранять медиа информацию из разных источников(телеграмм, телефон и тд) в централизованное хранилище.



МИКРОСЕРВИСЫ, ИЗ КОТОРЫХ СОСТОИТ ПРОЕКТ:
1) Основное файловое хранилище.
Хранение файлов будет осуществляться в seafile, однако код должен поддерживать безболезненный переезд на любое другое файловое хранилище(взаимодействие с файловым хранилищем должно идти строго через наш интерфейс).
Файловое хранилище должно хранить всю информацию, необходимаю для работы системы и для сохранения целостности и консистентности данных.
С основным файловым хранилищем взаимодействие идет только через сервис-обертку. Никто больше не имеет прямого доступа к основному файловому хранилищу. Файловое хранилище не обязательно находится в закрытой сети системы: сервис-обертка обращается к нему по TLS с учетными данными, известными только ей (см. раздел "ДОВЕРИЕ МЕЖДУ ВНУТРЕННИМИ СЕРВИСАМИ").

2) База данных.
Хранение информации, необходимой для работы проекта, но не связанной напрямую с самими файлами должно осуществляться в PostgreSQL. Из метаинформации о файлах в PostgreSQL хранится только та часть, которая нужна для фильтров и поиска файла по id, - индекс метаинформации (см. раздел "ИНДЕКС МЕТАИНФОРМАЦИИ"). Полная метаинформация лежит только в json файлах в файловом хранилище, и они являются источником истины.
С базой данных взаимодействие идет только через сервис-обертку. Никто больше не имеет прямого доступа к базе данных.

3) Сервис-обертка над базой знаний.
"База знаний" - это файловое хранилище и база данных вместе: все данные системы. Сервис-обертка над базой знаний - один сервис, который является единственной точкой доступа и к файловому хранилищу, и к базе данных. Отдельных оберток для файлового хранилища и для PostgreSQL нет: везде в этом документе "сервис-обертка" без уточнения означает этот один сервис. Позже могут появиться другие сервисы-обертки над чем-то еще, тогда они будут называться по тому, что оборачивают. Внутри он разделен на два независимых модуля с собственными интерфейсами: модуль файлового хранилища (за ним прячется seafile или любое другое хранилище) и модуль базы данных (за ним прячется PostgreSQL). Замена хранилища или базы меняет только соответствующий модуль.
Написан должен быть на python. Взаимодействие с PostgreSQL должно осуществляться через SQLAlchemy.
Для работы с сетью должен выступать FastAPI.
Собственной авторизации у сервиса-обертки нет: она не проверяет, какой внутренний сервис к ней обращается, и не ограничивает, к каким данным он имеет доступ (см. раздел "ДОВЕРИЕ МЕЖДУ ВНУТРЕННИМИ СЕРВИСАМИ").

4) Сервис обработки файлов.
Воркер, который обрабатывает файлы внутри системы. С сервисами-пользователями он не взаимодействует и запросов от них не получает.
Задания на обработку он получает через кафку от сервиса доступа к файлам. В задании приходит id операции, всю конкретику (что за файл, какой файл подменить, какую метаинформацию изменить) он берет из операции в postgres.
Получив задание о загруженном файле, он обрабатывает файл, если необходимо, перемещает его из места временного хранения в нужную директорию, создает файл с метаинформацией о нем и записывает в PostgreSQL индексную запись о файле. Подмену файла, изменение метаинформации файла (вместе с обновлением индексной записи) и удаление файла также выполняет он по заданию. Перед подменой или удалением он перемещает прежний файл и его json в корзину операции, а после успешного завершения операции по заданию на очистку удаляет корзину операции (см. раздел "ОПЕРАЦИИ", корзина операции).
При запуске системы на уже существующей базе знаний он же строит индекс метаинформации, сканируя файловое хранилище (см. раздел "ИНДЕКС МЕТАИНФОРМАЦИИ").
Каждое внесенное изменение он фиксирует в операции, а результат выполнения задания (успех или ошибка) через кафку сообщает сервису доступа к файлам.
Откат своих шагов (файловых изменений и индексных записей) также выполняет он, но только по команде: сервис доступа к файлам через кафку присылает задание на откат с id операции, сервис обработки файлов читает из операции зафиксированные шаги и отменяет их в обратном порядке, фиксируя каждую отмену в операции, после чего через кафку сообщает результат отката сервису доступа к файлам (см. раздел "ОПЕРАЦИИ"). Сам решения об откате он не принимает: при ошибке на своем шаге он сообщает об ошибке и ждет команды.
С файловым хранилищем и базой данных работает через сервис-обертку. В топик сервиса подписок сам не пишет: событие об изменении публикует сервис доступа к файлам после успешного завершения операции, потому что только он знает, что операция завершена, а не откачена.
Каждое задание может прийти из кафки повторно, поэтому все его шаги идемпотентны: перед действием шаг проверяет, не выполнено ли оно уже, и продолжает с первого незаписанного шага операции. Задания выполняются в пуле воркеров, а не в потоке консьюмера, оффсет подтверждается только после перевода операции в следующее состояние (см. раздел "ОПЕРАЦИИ", идемпотентность шагов и работа с кафкой).
Написан должен быть на python, сетевой слой - FastAPI.

5) Сервис авторизации.
Отвечает за прием заявок на регистрацию сервисов-пользователей, хранение одобренных сервисов-пользователей, выдачу bearer-token-ов и их проверку. Сервис обработки файлов этой логикой не занимается.
Мастер-ключа в системе нет. Регистрация идет через заявку: подать заявку может любой сервис-пользователь, но учетные данные он получает только после того, как администратор одобрит заявку в сервисе администрирования (см. раздел "АВТОРИЗАЦИЯ").
Предоставляет сервису администрирования внутренний API: вход администратора, список заявок, одобрение и отклонение заявки, блокировка и разблокировка сервиса-пользователя, отзыв его регистрации, перевыпуск его секрета. Вся логика рассмотрения заявок живет здесь, сервис администрирования только отображает ее.
Данные о заявках, зарегистрированных сервисах-пользователях и администраторах хранит в PostgreSQL через сервис-обертку. Секреты сервисов-пользователей и пароли администраторов хранит только в виде хеша.
Написан должен быть на python, сетевой слой - FastAPI.

6) Сервис доступа к файлам.
Все взаимодействие сервисов-пользователей с файлами идет через него: запросы на загрузку, подмену, скачивание и удаление файла, запросы и изменение метаинформации, запросы списка источников gateway направляет в сервис доступа к файлам.
Проверяет можно ли выполнить запрошенное действие с файлом (см. раздел "ПОЛИТИКА ДОСТУПА К ФАЙЛАМ") и выдает одноразовые токены с ttl на загрузку и скачивание файлов.
Метаинформацию о файлах по запросу сервиса-пользователя отдает он же: по индексу в PostgreSQL находит файлы, подходящие под id или фильтры, а полную метаинформацию читает из их json файлов в файловом хранилище.
На каждое действие сервиса-пользователя с файловым хранилищем, включая чтение (запрос метаинформации, скачивание), он создает в postgres операцию и ведет ее до завершения или отката (см. раздел "ОПЕРАЦИИ"). Сервису-пользователю он отдает id операции, и дальше сервис-пользователь общается с ним только по id операции.
Сам файлы он не обрабатывает и файловое хранилище не трогает ни при выполнении, ни при откате: задания на обработку загруженного файла, подмену файла, изменение метаинформации, удаление файла, откат файловых изменений и очистку корзины операции он через кафку передает сервису обработки файлов, указывая id операции. Сам он решает, когда операция завершена, а когда ее нужно откатить, и откатывает только собственные изменения в postgres (резервирование имени файла, одноразовые токены).
Если действие разрешено, сервис доступа к файлам фиксирует состояние файла (резервирует в postgres имя файла) и выдает одноразовый токен, привязанный к операции.
Одноразовый токен проверяет тот же сервис, который его выдает: сервис доступа к файлам является сервисом внешней авторизации (ext_authz) gateway для маршрутов загрузки и скачивания. Gateway, получив от сервиса-пользователя запрос на загрузку или скачивание файла, отправляет его заголовки сервису доступа к файлам, и только после его разрешения пропускает запрос в сервис-обертку. В ответ на проверку сервис доступа к файлам отдает все параметры действия из операции в виде заголовков, которые gateway добавляет к запросу: тип действия (загрузка или скачивание), путь в файловом хранилище, id операции, а для загрузки еще размер и хеш файла, заявленные сервисом-пользователем при создании операции. Сервис-обертка выполняет действие только по этим заголовкам (см. раздел "ОПЕРАЦИИ"). При проверке токена он же проверяет, что у сервиса-пользователя не превышен лимит одновременных передач, и что заявленный размер файла не превышает допустимый.
Результат каждой передачи (файл записан или прочитан целиком, либо передача оборвана) ему сообщает сервис-обертка, указывая id операции из заголовка.
Данные хранит в PostgreSQL через сервис-обертку.
Написан должен быть на python, сетевой слой - FastAPI.

7) Сервис подписок.
Используется для реализации подписок на изменения в файловом хранилище.
Принимает подписки от сервисов-пользователей, получает события об изменениях в файловом хранилище, формирует уведомления для подписанных сервисов-пользователей и через кафку отправляет их в сервис-нотифайер.
По запросу сервиса авторизации удаляет все подписки отозванного сервиса-пользователя и уведомляет всех, кто был подписан на его файлы, о том, что он отозвал регистрацию (см. раздел "ПОДПИСКА НА ИЗМЕНЕНИЯ В ФАЙЛОВОМ ХРАНИЛИЩЕ", уведомление об отзыве регистрации).
Написан должен быть на python, сетевой слой - FastAPI.

8) Сервис-нотифайер.
Занимается только отправкой уведомлений сервисам-пользователям. Уведомления получает через кафку от сервиса подписок и отправляет их сервисам-пользователям по web socket (см. раздел "ДОСТАВКА УВЕДОМЛЕНИЙ"). Web socket соединения сервисов-пользователей держит он сам: gateway их только проксирует, предварительно проверив bearer-token в сервисе авторизации. Сервис-нотифайер помнит, какому сервису-пользователю принадлежит каждое соединение, отправляет в него уведомления и ждет подтверждения.
По запросу сервиса авторизации закрывает все web socket соединения заблокированного или отозванного сервиса-пользователя.
В сервисе-нотифайере должна быть таблица с уведомлениями и политикой ретраев.
Политика ретраев должна быть экспоненциально затухающей: каждый следующий ретрай выполняется через в 2 раза большее время, чем предыдущий.
По запросу сервиса авторизации отменяет все недоставленные уведомления отозванного сервиса-пользователя.
Написан должен быть на python, сетевой слой - FastAPI.

9) Kafka.
Кафка используется только для взаимодействия между внутренними сервисами системы. Сервисы-пользователи с кафкой не взаимодействуют: все свои запросы они отправляют через gateway.
Через кафку сервис доступа к файлам передает задания сервису обработки файлов, сервис обработки файлов возвращает ему результаты выполнения заданий, сервис доступа к файлам после успешного завершения операции передает событие об изменении сервису подписок, а сервис подписок передает уведомления сервису-нотифайеру.

10) Gateway.
Единая точка входа для сервисов-пользователей. Сервис-пользователь не обращается к внутренним сервисам напрямую: все его запросы приходят в gateway, который перенаправляет их в нужный сервис (сервис авторизации, сервис доступа к файлам, сервис подписок, сервис-обертку, сервис-нотифайер).
Gateway - это Envoy Gateway, а не собственный сервис. Своего кода у gateway нет: вся его работа задается декларативной конфигурацией (маршруты, политики безопасности, политики трафика), которая хранится в репозитории рядом с кодом сервисов. Envoy Gateway работает поверх Kubernetes и Gateway API, поэтому система разворачивается в Kubernetes.
Что делает gateway сам, средствами Envoy: терминирует TLS, маршрутизирует запросы по путям в нужный сервис, применяет лимиты на частоту запросов и размер тела, держит таймауты, проксирует web socket соединения, отдает метрики Prometheus (см. раздел "TLS И ЛИМИТЫ GATEWAY").
Что gateway делать не может и поэтому делегирует внутренним сервисам через механизм внешней авторизации (ext_authz): перед тем как пропустить запрос, Envoy отправляет его заголовки во внешний сервис проверки и пропускает запрос дальше только если тот ответил разрешением. Таких сервисов проверки два:
1) Сервис авторизации - для всех маршрутов с bearer-token-ом, включая запрос на открытие web socket. Проверяет токен и в ответе добавляет к запросу заголовки с идентификатором сервиса-пользователя и временем протухания токена. Запросы, которые сервис авторизации не подтвердил, gateway дальше не пропускает. Исключение - подача заявки на регистрацию, запрос статуса заявки и запрос bearer-token-а: на этих маршрутах проверки нет, и gateway ограничивает их частоту по адресу отправителя;
2) Сервис доступа к файлам - для маршрутов загрузки и скачивания файлов. Проверяет одноразовый токен и в ответе добавляет к запросу заголовки с id операции, типом действия и путем в файловом хранилище из операции, а все заголовки с параметрами, которые прислал сервис-пользователь, велит удалить. Сервис-обертка берет путь и id операции только из этих заголовков: ничего из того, что сервис-пользователь прислал в запросе кроме токена и тела файла, в сервис-обертку не попадает.
Внутренние сервисы получают уже проверенные запросы и доверяют заголовкам, которые проставил gateway, потому что снаружи до них достучаться нельзя (см. раздел "ДОВЕРИЕ МЕЖДУ ВНУТРЕННИМИ СЕРВИСАМИ").
Web socket соединения gateway только проксирует: держит их и доставляет в них уведомления сервис-нотифайер (см. раздел "ДОСТАВКА УВЕДОМЛЕНИЙ"). Результат передачи файла сервису доступа к файлам сообщает сервис-обертка, потому что gateway сам ничего никому сообщать не умеет.
Когда я пишу, что сервис-пользователь обращается к какому-то внутреннему сервису, подразумевается, что он делает это через gateway.
Сервис администрирования через gateway не доступен: это внутренний сервис для администратора, а не для сервисов-пользователей.

11) Множество регистрируемых сервисов-пользователей.
Сервисы-пользователи должны подать заявку на регистрацию, дождаться ее одобрения администратором, получить свои учетные данные, после чего в своем life circle отправлять медиа в систему и/или получать медиа из нее.
Написаны могут быть на чем угодно.

12) Сервис администрирования.
Сервис с веб-интерфейсом для администратора системы. Веб-интерфейс - одностраничное приложение на React. Используется для приема заявок на регистрацию сервисов-пользователей: администратор видит список заявок с их названием, описанием и датой подачи, одобряет или отклоняет их с указанием причины. Там же администратор видит список зарегистрированных сервисов-пользователей, может заблокировать любой из них и перевыпустить его секрет.
Собственной бизнес-логики не содержит: все действия выполняет запросами во внутренний API сервиса авторизации. Напрямую к базе данных и к сервису-обертке не обращается.
Состоит из двух частей: React-приложение (frontend) и backend на python с FastAPI, который отдает собранное React-приложение как статику и проксирует его запросы в сервис авторизации. Браузер администратора общается только с этим backend-ом, напрямую в сервис авторизации из браузера запросы не идут: так в закрытой сети наружу торчит один адрес, сессия администратора живет на backend-е, а React-приложение не знает ни адресов, ни API внутренних сервисов.
Вход в интерфейс только по учетной записи администратора. Учетные данные администратора проверяет сервис авторизации. Первая учетная запись администратора создается при развертывании системы. Доступен только по TLS, попытки входа ограничены: не более 5 неудачных попыток в минуту с одного адреса, после чего адрес блокируется на 15 минут.
Наружу не публикуется и через gateway не доступен: доступ к нему есть только у администратора.
Ошибки работы системы (застрявшие откаты, недоставленные уведомления, блокировки по подбору секрета и т.д.) в сервис администрирования не попадают: он нужен только для заявок и управления сервисами-пользователями. Все такие события идут в логи и метрики (см. раздел "НАБЛЮДАЕМОСТЬ").
Кроме блокировки администратор может отозвать регистрацию сервиса-пользователя (см. раздел "АВТОРИЗАЦИЯ", отзыв регистрации).
Backend написан на python, сетевой слой - FastAPI. Frontend написан на React. Это единственное место в системе, где есть код не на python.

13) Prometheus.
Собирает метрики со всех внутренних сервисов. Каждый внутренний сервис отдает метрики в формате Prometheus на собственном эндпоинте /metrics, Prometheus опрашивает их по расписанию. Метрики PostgreSQL и Kafka собираются через их стандартные экспортеры.
Живет в закрытой сети, наружу не публикуется.

14) Grafana.
Визуализирует метрики из Prometheus и держит алерты по ним. Единственный интерфейс, через который администратор следит за состоянием системы: дашборды по операциям, очередям, уведомлениям и лимитам gateway, алерты на застрявшие откаты, рост ошибок, недоставленные уведомления и блокировки.
Доступна только администратору из закрытой сети по TLS, со своей учетной записью.



АВТОРИЗАЦИЯ:
За авторизацию отвечает отдельный сервис авторизации. Мастер-ключа в системе нет: у каждого сервиса-пользователя свой секрет, который он получает после одобрения заявки администратором.
Регистрация идет через заявку с ручным одобрением:
1) Сервис-пользователь подает заявку на регистрацию в сервис авторизации, передавая свое название и описание (кто он, какие источники будет присылать). Подать заявку может любой: bearer-token для этого запроса не нужен. В ответ сервис авторизации отдает id заявки. Id заявки - случайное непредсказуемое значение, его знает только подавший заявку сервис-пользователь, и по нему он потом забирает учетные данные;
2) Заявка попадает в состояние "ожидает" и появляется в сервисе администрирования. Администратор одобряет или отклоняет ее;
3) Сервис-пользователь периодически запрашивает статус заявки по ее id. Пока заявка не рассмотрена, он получает статус "ожидает". Если заявка отклонена, он получает статус "отклонена" и причину;
4) Если заявка одобрена, сервис авторизации при первом же запросе статуса после одобрения отдает сервису-пользователю его уникальный идентификатор и секрет. Секрет выдается ровно один раз: после выдачи заявка переходит в состояние "выдана", и повторный запрос статуса секрет не возвращает. В открытом виде секрет нигде не хранится, сервис авторизации хранит только его хеш. Если сервис-пользователь потерял секрет, администратор перевыпускает его через сервис администрирования, и новый секрет забирается тем же способом;
5) Дальше сервис-пользователь запрашивает bearer-token у сервиса авторизации, передавая свой идентификатор и секрет. После протухания сервис-пользователь перезапрашивает bearer-token.
Проверяет bearer-token тот же сервис, который его выдает, - сервис авторизации. Он является сервисом внешней авторизации (ext_authz) gateway: gateway, получив запрос от сервиса-пользователя, отправляет его заголовки сервису авторизации, тот проверяет токен и при успехе добавляет к запросу заголовки с идентификатором сервиса-пользователя и временем протухания токена. Внутренние сервисы получают уже проверенные запросы и узнают сервис-пользователя из этих заголовков.
Защита от подбора секрета живет в сервисе авторизации, а не в gateway: после 10 неудачных попыток получить bearer-token подряд выдача токена этому идентификатору блокируется на 15 минут. О блокировке сервис авторизации пишет в лог с уровнем WARNING и увеличивает метрику блокировок, по которой в Grafana настроен алерт.
Администратор может заблокировать сервис-пользователь через сервис администрирования: его bearer-token-ы перестают проходить проверку, новые не выдаются, сервис авторизации просит сервис-нотифайер закрыть его web socket соединения. Блокировка обратима: администратор может снять ее, после чего сервис-пользователь запрашивает новый bearer-token и продолжает работу. Подписки и недоставленные уведомления при блокировке сохраняются.
Одноразовые токены на загрузку и скачивание файлов к сервису авторизации не относятся: их выдает и проверяет сервис доступа к файлам.

Уникальность названия:
Название сервиса-пользователя уникально среди действующих (не отозванных) сервисов-пользователей и нерассмотренных заявок. Заявка с названием, которое занято действующим сервисом-пользователем или другой ожидающей заявкой, отклоняется сразу при подаче с указанием причины. Название - только для отображения; везде внутри системы (операции, метаинформация, индекс, подписки, уведомления) сервис-пользователь идентифицируется своим уникальным идентификатором, потому что название после отзыва регистрации может достаться другому сервису-пользователю, а идентификатор никогда не переиспользуется.

Отзыв регистрации (отзыв названия):
Регистрацию можно отозвать двумя путями: сам сервис-пользователь или администратор. Последствия одинаковые.
Схема отзыва самим сервисом-пользователем:
1) Сервис-пользователь отправляет запрос на отзыв своей регистрации в сервис авторизации, предъявив bearer-token. Никаких других параметров не нужно: отозвать можно только себя;
2) Сервис авторизации переводит сервис-пользователь в состояние "отозван": хеш секрета удаляется, все его bearer-token-ы перестают проходить проверку, новые не выдаются, название освобождается. Идентификатор остается в базе навсегда и никогда не выдается другому сервису-пользователю;
3) Сервис авторизации сообщает об отзыве сервису подписок (тот удаляет все его подписки и уведомляет его подписчиков об отзыве) и сервису-нотифайеру (тот закрывает web socket соединения сервиса-пользователя и отменяет его недоставленные уведомления);
4) Сервис-пользователь получает в ответе подтверждение отзыва. Отзыв необратим: чтобы снова работать с системой, нужно подать новую заявку, по которой будет выдан новый идентификатор;
5) Файлы, загруженные отозванным сервисом-пользователем, и их метаинформация остаются в системе без изменений. Операции отозванного сервиса-пользователя, которые на момент отзыва еще идут, доводятся до конца или откатываются по общим правилам, новые создать уже нельзя;
Схема отзыва администратором:
1) Администратор в сервисе администрирования выбирает сервис-пользователь и отзывает его регистрацию с указанием причины;
2) Сервис администрирования вызывает внутренний API сервиса авторизации, дальше все идет по шагам 2, 3 и 5 схемы выше. Сервис-пользователь узнает об отзыве по тому, что его bearer-token перестает проходить проверку, а запрос нового отвечает "регистрация отозвана" с причиной.



ОПЕРАЦИИ:
Взаимодействие сервиса-пользователя с файловым хранилищем должно быть транзакционным и атомарным. Реализуется это сагой.
Любое взаимодействие сервиса-пользователя с файловым хранилищем - это операция, без исключений. Для каждого такого взаимодействия (загрузка файла, подмена файла, изменение метаинформации, удаление файла, скачивание файла, запрос метаинформации, запрос списка источников) в postgres должна создаваться операция (operation). Это касается и чтения: запрос метаинформации, запрос списка источников и скачивание тоже операции, хотя сейчас у них нет шагов, которые нужно откатывать.
Операциями не являются только взаимодействия, не касающиеся файлового хранилища: заявки на регистрацию, получение bearer-token-а, отзыв регистрации, подписки.
Над одним файлом одновременно может идти только одна изменяющая операция (подмена, изменение метаинформации, удаление). Сервис доступа к файлам проверяет это при создании операции и отклоняет новую изменяющую операцию, пока предыдущая по этому файлу не завершена и не откачена. Одна операция при этом может охватывать несколько файлов (например, скачивание или удаление списка файлов): тогда проверка делается по каждому файлу из списка, и операция создается, только если она прошла для всех. Операции чтения (скачивание, запрос метаинформации) этим не ограничиваются, но если файл был удален до использования одноразового токена на скачивание, проверка токена завершается ошибкой "файл удален".
Создание операции инициирует сервис-пользователь. При создании он один раз сообщает всю конкретику: что это за операция, над каким файлом, с какой метаинформацией, из какого источника и тд. В ответ он получает id операции.
Дальше при общении с системой сервис-пользователь сообщает только id операции, а не ее конкретику. Изменить конкретику уже созданной операции нельзя: например нельзя запросить подмену одного файла, а потом сообщить id другого.
Одноразовые токены выдаются в рамках операции и привязаны к ней.
Операция - единственный источник всех параметров действия. Все, что нужно для выполнения шага (тип действия, путь во временном хранилище, конечный путь, id подменяемого файла, метаинформация, источник, сохранять ли имя), берется только из операции и никогда из запроса сервиса-пользователя или из сообщения в кафке. Это касается всех участников: gateway при загрузке и скачивании получает путь и тип действия от сервиса доступа к файлам из операции, сервис доступа к файлам при запросах по id операции берет конкретику из операции, сервис обработки файлов получает в задании только id операции и всю конкретику читает из операции. Параметры, присланные сервисом-пользователем после создания операции, игнорируются, а если они противоречат операции (например, другой путь), запрос отклоняется.
Операция фиксирует каждое изменение, которое было сделано в ходе ее выполнения (резервирование имени файла, загрузка файла в место временного хранения, перемещение файла, перемещение прежнего файла и его json в корзину операции, подмена файла, создание или изменение файла с метаинформацией, создание, изменение или удаление индексной записи в PostgreSQL). Шаги хранятся отдельной таблицей, записи в нее только добавляются и никогда не изменяются.
Машина состояний операции:
Операцию пишут два сервиса: сервис доступа к файлам и сервис обработки файлов. Чтобы они никогда не писали в нее одновременно (например, откат по таймауту поверх незавершенного перемещения файла), операция в каждый момент находится ровно в одном состоянии, и у каждого состояния ровно один владелец. Только владелец текущего состояния может добавлять шаги и переводить операцию в следующее состояние. Второй сервис в это время может только читать операцию и отправлять сообщения в кафку.
Состояния и их владельцы:
1) "создана" (владелец - сервис доступа к файлам): операция создана, параметры зафиксированы. Для загрузки и подмены - выдан одноразовый токен, ждем загрузку. Для скачивания - выданы токены, ждем передачи. Для изменения метаинформации и удаления это состояние мгновенное: сервис доступа к файлам сразу отправляет задание и переводит операцию в "в обработке". Для запроса метаинформации и списка источников операция проходит из "создана" в "завершена" внутри одного запроса;
2) "загружается" (владелец - сервис доступа к файлам): одноразовый токен на загрузку прошел проверку, сервис-обертка принимает тело файла. Переход из "создана" делает сервис доступа к файлам в момент проверки токена, поэтому повторное использование токена невозможно: второй запрос с тем же токеном увидит операцию уже не в "создана";
3) Из "загружается" операция выходит по сообщению сервиса-обертки о результате передачи: если файл записан целиком и его хеш совпал с заявленным, сервис доступа к файлам сразу отправляет задание и переводит операцию в "в обработке"; если передача оборвана или хеш не совпал - в "откатывается". Отдельного подтверждения от сервиса-пользователя не требуется: сервис-пользователь узнает о результате, запросив состояние операции по ее id;
4) "в обработке" (владелец - сервис обработки файлов): задание отправлено в кафку. Сервис обработки файлов выполняет шаги и записывает их. Сервис доступа к файлам в этом состоянии операцию не меняет ни по таймауту, ни по запросу сервиса-пользователя: все запросы по id операции отвечают текущим состоянием, не более. Закончив, сервис обработки файлов сам переводит операцию в "обработана" или в "ошибка обработки" и только после этого отправляет результат в кафку;
5) "обработана" (владелец - сервис доступа к файлам): все шаги выполнены. Сервис доступа к файлам завершает операцию: переводит в "завершена", публикует событие для подписок, отправляет задание на очистку корзины;
6) "ошибка обработки" (владелец - сервис доступа к файлам): сервис обработки файлов не смог выполнить шаг и остановился. Сервис доступа к файлам принимает решение об откате и переводит операцию в "откатывается";
7) "откатывается" (владелец - сервис обработки файлов): задание на откат отправлено. Сервис обработки файлов отменяет свои шаги в обратном порядке, записывая каждую отмену, и переводит операцию в "шаги откачены" или, если отмена не удалась, оставляет в "откатывается" и сообщает об ошибке. Если шагов сервиса обработки файлов в операции нет, сервис доступа к файлам минует это состояние и переходит из "откатывается" сразу в "откачена" сам: в этом случае владелец "откатывается" - он;
8) "шаги откачены" (владелец - сервис доступа к файлам): файловое хранилище и индекс возвращены в исходное состояние. Сервис доступа к файлам откатывает свои изменения в postgres (резервирование имени, токены) и переводит операцию в "откачена";
9) "завершена", "откачена", "ошибка" - конечные состояния, из них переходов нет. "ошибка" - для операций, которые отклонены на создании (не прошла проверка) или отклонены на синхронном выполнении (запрос метаинформации, списка источников);
10) "требует вмешательства" (владелец - никто): откат не удался за отведенное время. Из этого состояния операцию выводит только человек, см. раздел "НАБЛЮДАЕМОСТЬ".
Переходы выполняются только через сравнение с ожидаемым состоянием (compare-and-set): сервис-обертка предоставляет операцию "перевести операцию из состояния X в состояние Y", которая выполняется одним атомарным запросом к PostgreSQL с условием на текущее состояние и номер версии операции и возвращает, удался ли переход. Если переход не удался, инициатор перечитывает операцию и действует по ее фактическому состоянию, а не повторяет свой переход вслепую. Так же устроено добавление шага: сервис-обертка добавляет шаг только если операция в указанном состоянии, иначе отказывает.
Таймауты привязаны к состояниям, а не к операции в целом, и каждый таймаут проверяет только владелец состояния:
1) "создана" для загрузки и подмены: ttl одноразового токена. "загружается": максимальная длительность передачи. "создана" для скачивания: ttl токенов. Истечение любого из них проверяет сервис доступа к файлам фоновой задачей по полю "крайний срок" операции и переводит операцию в "откатывается" (для скачивания - в "завершена");
2) "в обработке" и "откатывается": максимальная длительность задания. Ее держит сам сервис обработки файлов: если задание не укладывается, он прерывает его и переводит операцию в "ошибка обработки" (или оставляет в "откатывается" с ошибкой). Сервис доступа к файлам в этих состояниях по таймауту ничего не делает, но если результата нет дольше ожидаемого, пишет в лог с уровнем ERROR и увеличивает метрику зависших заданий;
3) "откатывается" с повторяющимися ошибками: общий предельный срок отката, после которого сервис доступа к файлам (получив очередной результат с ошибкой) переводит операцию в "требует вмешательства".
Сообщения в кафке и состояния: каждое задание и каждый результат несут id операции и состояние, в котором операция была в момент отправки. Получатель перед выполнением перечитывает операцию и, если она уже не в этом состоянии, сообщение не выполняет, а пишет в лог с уровнем WARNING как устаревшее. Это защищает от повторной доставки и от сообщений, отправленных до того, как состояние изменилось.
Падение сервиса обработки файлов посреди задания: оффсет в кафке не подтвержден, после перезапуска задание придет снова. Операция по-прежнему в "в обработке" с частично записанными шагами. Сервис обработки файлов читает уже записанные шаги и продолжает с первого невыполненного; каждый шаг устроен так, что его повторное выполнение не ломает результат (проверить, что файл уже на месте, прежде чем перемещать, и т.п.). Шаг записывается в операцию после фактического выполнения, поэтому упавший между выполнением и записью шаг будет выполнен повторно, и именно поэтому он обязан быть идемпотентным.
Идемпотентность шагов:
Все пути, с которыми работает шаг, выводятся из операции, поэтому повтор шага всегда работает с теми же путями. Каждый шаг перед действием проверяет, не выполнено ли оно уже, и действует по фактическому состоянию хранилища:
1) Перемещение файла (из временного хранилища в конечный путь, в корзину операции, из корзины обратно): если целевой путь занят, а исходный пуст - шаг уже выполнен, ничего не делать. Если исходный занят, а целевой пуст - выполнить перемещение. Если заняты оба - сравнить размер и хеш: совпадают - удалить исходный и считать шаг выполненным, не совпадают - ошибка шага. Затереть чужой файл при этом невозможно: имя по целевому пути зарезервировано этой операцией, а над файлом не может идти другая изменяющая операция. Если пусты оба - данные потеряны, это ошибка шага, которая откатом не лечится: лог с уровнем ERROR, метрика, операция уходит в "ошибка обработки" и дальше в откат того, что откатить можно;
2) Запись json файла с метаинформацией: содержимое детерминировано выводится из операции и прежнего json (который к этому моменту лежит в корзине операции), поэтому повторная запись дает тот же файл. Пишется во временное имя рядом и затем переименовывается, чтобы в хранилище никогда не было полузаписанного json;
3) Индексная запись: только upsert по id файла и delete по id файла, оба безразличны к повтору;
4) Компенсации: те же правила в обратную сторону. Повторная отмена уже отмененного шага не ошибка.
Работа с кафкой в сервисе обработки файлов:
1) Оффсет сообщения подтверждается вручную и только после того, как операция переведена в следующее состояние ("обработана", "ошибка обработки", "шаги откачены") и результат отправлен. Падение до этого момента означает повторную доставку задания, что безопасно благодаря возобновлению с первого незаписанного шага;
2) Продьюсеры у всех сервисов работают с включенной идемпотентностью, чтобы повторы при отправке в кафку не порождали дублей сообщений;
3) Задания выполняются не в потоке консьюмера, а в пуле воркеров. Перемещение файла в десятки гигабайт занимает минуты, и если консьюмер в это время не опрашивает брокер, брокер считает его мертвым, запускает перебалансировку и отдает партицию другому экземпляру, который начнет то же задание параллельно с еще идущим. Поэтому поток консьюмера только опрашивает брокер, на время выполнения задания ставит партицию на паузу и снимает с паузы после подтверждения оффсета. Число воркеров и число одновременно обрабатываемых партиций задается конфигурацией;
4) Несколько экземпляров сервиса обработки файлов делят партиции между собой, и одна операция всегда попадает в один экземпляр, потому что ключ партиционирования - id операции. Двух экземпляров, одновременно выполняющих задания одной операции, не бывает, кроме короткого окна при перебалансировке, которое закрывается правилом 3 и машиной состояний.
Корзина операции:
Шаги, которые уничтожают существующие данные (подмена файла, удаление файла, изменение json с метаинформацией), нельзя откатить, если прежние данные потеряны. Поэтому сервис обработки файлов перед таким шагом перемещает прежний файл и/или его json в корзину операции: директорию trash/<id операции>/ на верхнем уровне файлового хранилища рядом с file_storage/ и metadata/. Корзина не индексируется и сервисам-пользователям не видна. При откате сервис обработки файлов возвращает данные из корзины на место. После успешного завершения операции сервис доступа к файлам через кафку отправляет сервису обработки файлов задание на очистку корзины операции, и тот удаляет trash/<id операции>/. Очистка не является шагом операции и на ее результат не влияет: операция уже завершена. Если очистка не удалась, она повторяется с экспоненциально растущим интервалом, а количество неочищенных корзин видно в метриках.
Если на каком-то шаге произошла ошибка или сервис-пользователь не завершил операцию за отведенное время, то все уже зафиксированные изменения должны быть откачены в обратном порядке: файловое хранилище и postgres должны вернуться в состояние до начала операции.
Откат идет так:
1) Решение об откате принимает только сервис доступа к файлам и только в состояниях, которыми он владеет: по состоянию "ошибка обработки", по обрыву загрузки или несовпадению хеша в "загружается", по истечению крайнего срока в "создана" или "загружается". Он переводит операцию в состояние "откатывается" через compare-and-set; с этого момента запросы сервиса-пользователя по этой операции и ее одноразовые токены отклоняются. Пока операция в "в обработке", откат невозможен: сервис доступа к файлам ждет, когда сервис обработки файлов сам выйдет из этого состояния;
2) Если в операции зафиксированы шаги сервиса обработки файлов (файл во временном хранилище, перемещение, перемещение в корзину операции, подмена, создание или изменение файла с метаинформацией, создание, изменение или удаление индексной записи), сервис доступа к файлам через кафку отправляет сервису обработки файлов задание на откат с id операции. Сервис обработки файлов отменяет эти шаги в обратном порядке, фиксируя каждую отмену в операции, и через кафку сообщает результат. Файл, загруженный во временное хранилище, тоже удаляет он, хотя записал его туда gateway;
3) Сервис обработки файлов, откатив свои шаги, переводит операцию в "шаги откачены" и сообщает результат. Сервис доступа к файлам (или сразу, если шагов сервиса обработки файлов в операции не было) откатывает свои изменения в postgres (снимает резервирование имени, аннулирует одноразовые токены) и переводит операцию в состояние "откачена";
4) Если откат шагов сервиса обработки файлов завершился ошибкой, операция остается в состоянии "откатывается", и сервис доступа к файлам повторяет задание на откат с экспоненциально растущим интервалом. Отмена шага должна быть идемпотентной: повторная отмена уже отмененного шага не является ошибкой. Если откат не удается дольше отведенного времени, операция помечается как требующая ручного вмешательства: сервис доступа к файлам пишет об этом в лог с уровнем ERROR и id операции и увеличивает метрику операций, застрявших в откате, по которой в Grafana настроен алерт (см. раздел "НАБЛЮДАЕМОСТЬ"). В сервис администрирования такие события не попадают;
Задания для сервиса обработки файлов по одной операции обрабатываются строго последовательно: ключом партиционирования в кафке служит id операции. Вместе с машиной состояний это дает двойную защиту: задание на откат не может быть отправлено, пока операция в "в обработке" (владелец другой), а если бы и было, оно выполнилось бы только после текущего задания и было бы отброшено как устаревшее по несовпадению состояния.
Операция либо выполняется целиком, либо не оставляет после себя никаких изменений.
Результат каждой передачи файла по одноразовому токену (загрузка или скачивание) сервису доступа к файлам сообщает сервис-обертка, которая эту передачу выполняла: передача завершена успешно или оборвана (тело короче заявленного, соединение разорвано, превышен размер, хеш не совпал). Id операции, а для загрузки и заявленные размер и хеш, она берет из заголовков, которые проставил gateway по результату проверки токена. При загрузке сервис-обертка считает хеш потоком во время записи, по окончании сравнивает его и фактический размер с заявленными и только при совпадении считает передачу успешной. Сервис доступа к файлам фиксирует результат в операции как шаг. Для загрузки успешная передача сразу ведет к отправке задания на обработку, а оборванная или с несовпавшим хешем - к откату операции; негодный временный файл сервис-обертка удаляет сама сразу, до отката, чтобы не оставлять мусор.
Контрольная сумма файла:
При создании операции загрузки или подмены сервис-пользователь обязан передать размер файла в байтах и его хеш (SHA-256 в шестнадцатеричной записи). Оба значения записываются в операцию и изменению не подлежат. По ним система проверяет целостность загруженного файла, а после обработки хеш сохраняется в разделе "system" метаинформации и в индексе. Хеш нужен и для проверки при скачивании: сервис-пользователь получает его вместе с метаинформацией и может сверить скачанный файл сам. Операция без размера или хеша отклоняется при создании.
Операция скачивания:
Скачивание идет через операцию, хотя сейчас у нее нет шагов, которые нужно откатывать. Это сделано намеренно: позже при чтении могут появиться изменения (например, учет обращений к файлу или пометка файла), и они должны лечь в тот же механизм операции, а не в отдельный. Пока таких шагов нет, операция скачивания фиксирует только факт запроса, выданные токены и результат каждой передачи.
Операция запроса списка источников:
Устроена так же, как операция запроса метаинформации: создается при запросе, фиксирует, кто запрашивал и для какого источника запрошены подисточники (или что запрошен верхний уровень), сколько источников найдено, выполняется и завершается в рамках одного запроса, в ответе указан id операции. Токенов не выдает, заданий не порождает, событий для подписок не порождает.
Операция удаления файла:
Создается при запросе удаления по id файла или списку id файлов, выполняется сервисом обработки файлов по заданию через корзину операции и после успешного завершения порождает событие "удаление файла" для сервиса подписок по каждому удаленному файлу. Удаление списка атомарно: либо удалены все файлы из списка, либо ни один. Подробная схема в разделе "УДАЛЕНИЕ ФАЙЛОВ СЕРВИСОМ-ПОЛЬЗОВАТЕЛЕМ ИЗ ФАЙЛОВОГО ХРАНИЛИЩА".
Операция запроса метаинформации:
Создается при запросе метаинформации и фиксирует, кто запрашивал, какие id файлов или какие фильтры были переданы и сколько файлов найдено. Выполняется и завершается в рамках одного запроса: сервис доступа к файлам создает операцию, выполняет поиск и чтение метаинформации, фиксирует результат и завершает операцию, после чего отдает ответ, в котором кроме метаинформации указан id операции. Одноразовые токены в ней не выдаются, заданий сервису обработки файлов она не порождает. Если поиск или чтение завершились ошибкой, операция завершается с ошибкой. Событий для сервиса подписок не порождает.
Жизненный цикл операции скачивания:
1) Создается, когда сервис-пользователь запрашивает файл/файлы. В ней фиксируются id запрошенных файлов и выданные на них одноразовые токены;
2) По каждому файлу сервис-обертка после передачи сообщает сервису доступа к файлам результат, и тот фиксирует его в операции: файл передан или передача оборвана. Оборванная передача откатом не считается: токен уже использован, сервис-пользователь создает новую операцию скачивания;
3) Операция завершается, когда по всем выданным токенам получен результат либо когда истек ttl токенов. В завершенной операции видно, какие файлы были переданы, а какие нет. Отдельного сообщения "скачал" от сервиса-пользователя не требуется;
4) Если у операции скачивания появятся шаги, меняющие состояние, они будут выполняться и откатываться по общим правилам операций.
Событий для сервиса подписок операция скачивания не порождает.
Ведет операции сервис доступа к файлам. Сервис обработки файлов выполняет свои шаги операции и их откат по команде и сообщает ему результат.
Сообщение об изменении в топик сервиса подписок пишет сервис доступа к файлам и только после успешного завершения операции. Откаченные операции и операции чтения (скачивание, запрос метаинформации, запрос списка источников) событий не порождают. В событии передаются тип изменения (добавление файла, подмена файла, изменение метаинформации, удаление файла), id файла, id операции, идентификатор и текущее название сервиса-пользователя, выполнившего операцию, и метаинформация файла после изменения (для удаления - метаинформация на момент удаления), чтобы сервис подписок мог применить фильтры, не обращаясь к хранилищу.



ОТПРАВКА ФАЙЛОВ СЕРВИСОМ-ПОЛЬЗОВАТЕЛЕМ В ФАЙЛОВОЕ ХРАНИЛИЩЕ:
Обшая последовательная схема:
Когда я пишу, что какой-то сервис пишет файл в файловое хранилище, подразумевается, что он делает это через сервис-обертку.
1) Сервис-пользователь, согласно своей внутренней логике, получает файл, который нужно сохранить в файловое хранилище;
2) Сервис-пользователь отправляет всю метаинформацию, касающуюся файла, а также его размер в байтах и хеш SHA-256 запросом в сервис доступа к файлам;
3) Сервис доступа к файлам получает метаинформацию, размер и хеш, создает операцию и проверяет можно ли загрузить файл в файловое хранилище (в том числе что размер не превышает допустимый);
4) Если загрузить файл нельзя, то сервис доступа к файлам завершает операцию с ошибкой и сообщает об этом сервису-пользователю в ответе на запрос;
5) Если загрузить файл можно, то сервис доступа к файлам фиксирует состояние этого файла, чтобы никто другой не мог каким-то образом помешать дальнейшей загрузке файла в файловое хранилище(резервирует в postgres имя файла, чтобы другой сервис-пользователь не мог его занять). Путь во временном хранилище, по которому будет загружен файл, он записывает в операцию. После отдает сервису-пользователю в ответе на запрос id операции, одноразовый токен с ttl и url gateway, по которому файл необходимо загрузить. Этот токен должен давать возможность загрузить файл только по пути, записанному в операции;
6) Сервис-пользователь отправляет файл по этому url в gateway, передавая только одноразовый токен и тело файла. Gateway через ext_authz проверяет токен в сервисе доступа к файлам, получает от него заголовки с id операции, путем во временном хранилище, заявленными размером и хешем из операции и проксирует запрос в сервис-обертку. Сервис-обертка сохраняет файл по пути из заголовка (в seafile это специальная директория, в S3 это будет просто специальный подпуть), считая хеш по ходу записи, сверяет фактические размер и хеш с заявленными и сообщает сервису доступа к файлам результат передачи. Путь от сервиса-пользователя не принимается;
7) Если файл записан целиком и хеш совпал, сервис доступа к файлам через кафку передает задание на обработку файла сервису обработки файлов, указывая id операции. Отдельного сообщения "файл загружен" от сервиса-пользователя не требуется: о ходе операции он узнает, запрашивая ее состояние по id. Если передача оборвана или хеш не совпал, операция откатывается, а сервис-пользователь видит это в состоянии операции и может создать новую;
8) Сервис обработки файлов обрабатывает файл, если необходимо, перемещает его в нужную директорию, создает файл с метаинформацией о файле и записывает индексную запись о файле в PostgreSQL. Каждое изменение он фиксирует в операции;
9) Сервис обработки файлов через кафку сообщает результат сервису доступа к файлам. При успехе операция завершается, и сервис доступа к файлам пишет событие об изменении в топик сервиса подписок. При ошибке все изменения, сделанные в рамках операции, откатываются, событие не пишется;

Когда сервис-пользователь отправляет медиа он должен также отправлять информацию об источнике этой медиа. Источник может быть вложенным. Передавать необходимо списком, где каждый следующий элемент это подкаталог. Файлы в файловом хранилище должны группироваться соответственно источнику. Если источник вложенный, то должно формироваться дерево каталогов.

Вместе с самим файлом в файловое хранилище должен сохраняться json файл с метаинформацией о нем.
Этот json файл необходимо сохранять по тому же пути, но в другую директорию на верхнем уровне. Имя json файла - это полное имя файла вместе с его расширением плюс ".json", чтобы файлы с одинаковым именем и разными расширениями в одном источнике (например, video_1.mp4 и video_1.png) не претендовали на один и тот же json файл.
Например если файл сохранен по пути "<путь_к_корневой_директории_проекта>/file_storage/youtube/channel_name/video_1.mp4", то json файл с метаинформацией должен быть сохранен в "<путь_к_корневой_директории_проекта>/metadata/youtube/channel_name/video_1.mp4.json". Для файла без расширения с именем "readme" json файл будет "readme.json".
Json файл с метаинформацией имеет два раздела на верхнем уровне: "system" и "custom". Раздел "system" заполняет только система. Раздел "custom" разбит по сервисам-пользователям: его ключи - это идентификаторы сервисов-пользователей, которые добавляли метаинформацию к этому файлу, а значение каждого такого ключа - json-объект с полями этого сервиса-пользователя. Других ключей на верхнем уровне нет. Благодаря этому имена пользовательских полей никогда не пересекаются ни с системными, ни с полями других сервисов-пользователей: каждый сервис-пользователь волен называть свои поля как угодно, в том числе так же, как называются системные поля или поля другого сервиса-пользователя.
В раздел "system" сервис обработки файлов должен сохранять:
1) Уникальный id файла(UUID);
2) Название файла;
3) Расширение файла;
4) Вес файла в байтах и хеш SHA-256 его содержимого;
5) Дату и время добавления файла;
6) Сервис-пользователь, приславший файл: его идентификатор и название на момент отправки;
7) Источник, откуда сервис-пользователь взял файл;
8) Дату и время последнего изменения файла или его метаинформации и сервис-пользователь, сделавший это изменение: его идентификатор и название на момент изменения. При загрузке совпадают с датой добавления и приславшим сервисом-пользователем;
9) Авторство пользовательской метаинформации: для каждого сервиса-пользователя, у которого есть пространство в разделе "custom", - его название на момент последнего изменения и для каждого его ключа верхнего уровня дата добавления и дата последнего изменения. Хранится в "system" в виде объекта той же формы, что и "custom": идентификатор сервиса-пользователя, внутри - его ключи. Заполняет и обновляет только система;
10) Возможно ещё какие-то поля;

ИНДЕКС МЕТАИНФОРМАЦИИ
Json файлы с метаинформацией в файловом хранилище - единственный источник истины о метаинформации. В PostgreSQL хранится только индекс: та часть метаинформации, без которой нельзя реализовать фильтры и найти файл по id. Индекс можно в любой момент полностью перестроить по json файлам, ничего кроме них для этого не нужно.
В индексной записи хранится:
1) Уникальный id файла;
2) Путь к файлу и путь к его json файлу в файловом хранилище;
2а) Размер файла и хеш SHA-256 его содержимого;
3) Расширение файла;
4) Источник в виде пути (список элементов источника, склеенный в путь), чтобы фильтр по источнику с подисточниками работал как поиск по префиксу;
5) Идентификатор сервиса-пользователя, добавившего файл, и идентификатор сервиса-пользователя, последним изменившего файл или его метаинформацию;
6) Дата и время добавления и последнего изменения;
7) Возможно ещё какие-то поля, если под них появятся фильтры;
Пользовательская метаинформация в индекс не попадает.
Индекс обновляется только в рамках операции: создание или изменение индексной записи - отдельный шаг операции, который выполняет сервис обработки файлов сразу после создания или изменения json файла. Этот шаг фиксируется в операции и откатывается вместе с остальными при откате операции. Отдельного воркера, который синхронизирует индекс с хранилищем, нет.
При расхождении индекса и json файла прав json файл. Если сервис доступа к файлам при чтении метаинформации обнаруживает, что json файл по пути из индекса отсутствует или не соответствует индексной записи, он пишет об этом в лог с уровнем ERROR и увеличивает соответствующую метрику.
Построение индекса при запуске:
1) При старте сервис обработки файлов проверяет, пуст ли индекс. Если индекс пуст, а файловое хранилище нет (система запущена на уже существующей базе знаний), он сканирует директорию metadata/ файлового хранилища, читает каждый json файл и создает по нему индексную запись;
2) Пока сканирование не завершено, сервис обработки файлов задания из кафки не берет, а сервис доступа к файлам отклоняет создание операций и запросы метаинформации с ответом "система инициализируется". Ход сканирования виден в метриках;
3) Полное перестроение индекса можно запустить вручную через конфигурацию сервиса обработки файлов при его перезапуске: индекс очищается и строится заново по той же процедуре. Это единственный способ починить индекс после сбоя;
4) Json файл, который не удается прочитать или разобрать, при сканировании пропускается с записью в лог с уровнем ERROR, остальные файлы индексируются.

Сервис-пользователь при отправке файла должен иметь возможность добавить свою метаинформацию о файле. Подаваться должно в формате json-объекта, который 1 в 1 становится содержимым пространства этого сервиса-пользователя в разделе "custom": custom.<идентификатор сервиса-пользователя>. Если сервис-пользователь свою метаинформацию не прислал, раздел "custom" сохраняется пустым объектом, пространство для него не создается. Единственное требование к пользовательской метаинформации - это валидный json-объект (не массив и не скаляр) в пределах лимита на размер тела запроса; если это не так, сервис доступа к файлам отклоняет создание операции и сообщает об этом сервису-пользователю. Проверок на имена полей нет: коллизий с системными полями и с полями других сервисов-пользователей быть не может, потому что они лежат в других разделах и пространствах.
Раздел "system" сервис-пользователь менять не может ни при загрузке, ни при редактировании: все его поля заполняет и обновляет только система.
Пространства сервисов-пользователей в разделе "custom" и авторство ключей:
Раздел "custom" устроен как объект, ключи которого - идентификаторы сервисов-пользователей (именно идентификаторы, а не названия: название после отзыва регистрации может достаться другому сервису-пользователю, идентификатор - никогда). Значение каждого ключа - пространство этого сервиса-пользователя: json-объект с его полями, хранящийся ровно так, как он его прислал, без обертывания. Правила:
1) Каждый сервис-пользователь пишет только в свое пространство: добавляет, обновляет и удаляет поля только в custom.<свой идентификатор>. Чужие пространства он видит при запросе метаинформации, но изменить не может: операция изменения метаинформации не принимает идентификатор пространства, оно всегда равно идентификатору сервиса-пользователя, создавшего операцию;
2) Пространство появляется, когда сервис-пользователь впервые добавляет к файлу хотя бы одно поле, и исчезает, когда он удаляет последнее. Пространства разных сервисов-пользователей независимы: одинаковые имена полей в разных пространствах - это разные поля;
3) Кто добавил и кто последним изменил поле, следует из пространства: это всегда его владелец. Поэтому в поле авторства раздела "system" хранится объект той же формы, что и "custom": на каждое пространство - название сервиса-пользователя на момент его последнего изменения, и на каждый ключ верхнего уровня пространства - дата добавления и дата последнего изменения. Авторство ведется по ключам верхнего уровня пространства: если значение ключа - вложенный объект, изменение чего угодно внутри него считается изменением этого ключа;
4) При загрузке файла раздел "custom" содержит одно пространство - приславшего сервиса-пользователя (или пусто, если он метаинформацию не прислал), все его ключи получают дату добавления и дату изменения, равную дате загрузки;
5) При удалении ключа его запись об авторстве удаляется вместе с ним, при удалении последнего ключа - вместе с пространством. Запись об авторстве и значение ключа всегда меняются в одном шаге операции, поэтому расхождений между ними не бывает;
6) Сервис-пользователь получает весь раздел "custom" со всеми пространствами и авторство вместе с остальной метаинформацией при ее запросе, в событиях для подписок они тоже есть;
7) Пространство отозванного сервиса-пользователя остается в файле как есть: его идентификатор не переиспользуется, а название на момент последнего изменения записано в авторстве.

Сервис-пользователь при отправке файла должен указывать нужно ли сохранять имя файла или нет. Если имя сохранять не нужно, то сервис обработки файлов должен переименовать файл при помощи UUID. Если имя нужно сохранять, но в файловом хранилище файл с таким именем по такому пути уже существует, то необходимо не сохранять файл и сообщить об этом сервису-пользователю.



ПОЛУЧЕНИЕ ФАЙЛОВ СЕРВИСОМ-ПОЛЬЗОВАТЕЛЕМ ОТ ФАЙЛОВОГО ХРАНИЛИЩА
Должно быть 3 пути:
1) Запрос метаинформации по файлу/файлам;
2) Запрос самого файла;
3) Запрос списка источников;

Общая последовательная схема запроса метаинформации по файлу/файлам:
1) Сервис-пользователь запрашивает у сервиса доступа к файлам метаинформацию по id файла/файлов или фильтрам;
2) Сервис доступа к файлам создает операцию запроса метаинформации, по индексу в PostgreSQL находит подходящие файлы, читает их json файлы из файлового хранилища через сервис-обертку, фиксирует результат в операции и завершает ее;
3) В ответе на запрос сервис доступа к файлам отправляет всю метаинформацию по запрашиваемому файлу/файлам и id операции;

Общая последовательная схема запроса файла/файлов:
Когда я пишу, что какой-то сервис пишет файл в файловое хранилище, подразумевается, что он делает это через сервис-обертку.
1) Сервис-пользователь запрашивает у сервиса доступа к файлам файл/файлы по его/их id;
2) Сервис доступа к файлам создает операцию и проверяет можно ли скачать файл/файлы (файлы существуют, см. раздел "ПОЛИТИКА ДОСТУПА К ФАЙЛАМ"). Если можно, то в ответе на запрос дает сервису-пользователю id операции, одноразовый токен с ttl на каждый запрашиваемый файл и url/url-ы, по которому надо скачать файл/файлы. Токен должен позволять скачать файл только по конкретному пути;
3) Сервис-пользователь скачивает файлы по этим url в gateway, передавая только одноразовый токен. Gateway через ext_authz проверяет токен в сервисе доступа к файлам, получает от него заголовки с id операции и путем файла в файловом хранилище из операции и проксирует запрос в сервис-обертку, которая отдает файл по пути из заголовка. Путь от сервиса-пользователя не принимается;
4) После передачи каждого файла сервис-обертка сообщает сервису доступа к файлам результат (передан или оборван), тот фиксирует его в операции. Когда получены результаты по всем токенам или истек их ttl, операция скачивания завершается (см. раздел "ОПЕРАЦИИ");

Должны быть фильтры:
1) По сервису-пользователю, который добавил/изменил файл;
2) По источнику файла(если у указанного источника есть подисточники, то возвращать нужно рекурсивно все файлы из подисточников);
3) По типу файла (png, mp4, pdf и т.д.);
4) Возможно ещё какие-то фильтры;

Общая последовательная схема запроса списка источников:
Источники не хранятся отдельной сущностью: источник существует, пока в нем или в его подисточниках есть хотя бы один файл, и список источников вычисляется по индексу метаинформации (по полю "источник в виде пути"). Пустые директории в файловом хранилище источниками не являются.
Дерево источников целиком за один запрос не отдается. Листинг идет поэтапно, уровень за уровнем:
1) Сервис-пользователь запрашивает у сервиса доступа к файлам верхнеуровневые источники, не передавая родительский источник;
2) Сервис доступа к файлам создает операцию запроса списка источников, по индексу находит все различные первые элементы источников и для каждого отдает: название, есть ли у него подисточники, количество файлов непосредственно в нем (без подисточников). Операцию он завершает и в ответе указывает ее id;
3) Чтобы спуститься глубже, сервис-пользователь запрашивает подисточники выбранного источника, передавая его в виде списка элементов (как при загрузке файла). Сервис доступа к файлам в новой операции отдает подисточники этого источника в том же формате: только следующий уровень, без внуков;
4) Сервис-пользователь повторяет шаг 3 для каждого источника, у которого есть подисточники, пока не обойдет нужную ему часть дерева. Каждый такой запрос - отдельная операция;
Если переданного источника не существует, сервис доступа к файлам завершает операцию с ошибкой и сообщает об этом в ответе.



РЕДАКТИРОВАНИЕ ФАЙЛОВ СЕРВИСОМ-ПОЛЬЗОВАТЕЛЕМ В ФАЙЛОВОМ ХРАНИЛИЩЕ:
Сервис-пользователь должен иметь возможность редактировать файлы, уже загруженные на файловый сервер.
Должна быть возможность:
1) Подменить сам файл;
2) Добавить поля в свое пространство раздела "custom" метаинформации;
3) Обновить или удалить существующие поля своего пространства раздела "custom";
4) Возможно ещё что-то;
Редактировать можно только свое пространство в разделе "custom": при создании операции изменения метаинформации сервис-пользователь передает json-объект с полями, которые нужно добавить или обновить, и список имен полей, которые нужно удалить. Пространство определяется идентификатором сервиса-пользователя, создавшего операцию, и в параметрах операции не передается. Сервис обработки файлов применяет изменения к этому пространству в текущем json файле, остальные поля этого пространства и чужие пространства не трогает; если пространства еще нет, оно создается, если после удаления в нем не осталось полей, оно удаляется. Одновременно он обновляет авторство ключей в разделе "system": для добавленного ключа записывает дату добавления и дату изменения, для обновленного - только дату изменения, для удаленного удаляет запись, и обновляет название сервиса-пользователя в записи о пространстве. Ключ, значение которого прислано таким же, каким оно уже было, считается измененным: система значения не сравнивает. Раздел "system" сервис-пользователь изменить не может: в нем система сама обновляет дату и время последнего изменения, сервис-пользователь, последним изменивший файл, и авторство ключей.

Общая последовательная схема подмены файла такая же, что и при загрузке файла, но файл должен не просто загружаться, а подменять существующий, id которого сервис-пользователь сообщил сервису доступа к файлам при создании операции. Этот id сохраняется в операции и после ее создания измениться не может: дальше сервис-пользователь сообщает только id операции, и сервис обработки файлов берет id подменяемого файла из операции. Id файла при подмене не меняется.
Главное отличие от загрузки: подмена уничтожает прежний файл, и чтобы ее можно было откатить, прежний файл до коммита никуда не исчезает, а лежит в корзине операции и удаляется только после успешного завершения операции.
Пошагово:
1) Сервис-пользователь создает операцию подмены, передавая id подменяемого файла, размер и хеш SHA-256 нового файла и, при желании, новую пользовательскую метаинформацию. Сервис доступа к файлам проверяет, что файл существует и над ним не идет другая изменяющая операция, записывает в операцию id файла и путь во временном хранилище и отдает id операции, одноразовый токен и url для загрузки. Имя файла не резервируется: оно уже принадлежит подменяемому файлу;
2) Сервис-пользователь загружает новый файл по этому url во временное хранилище так же, как при загрузке (шаг 6 схемы загрузки); размер и хеш нового файла он передал при создании операции, и сервис-обертка сверяет их так же, как при загрузке. Подменяется только содержимое файла: имя, расширение и путь остаются прежними. Если расширение загруженного файла отличается от расширения подменяемого, сервис доступа к файлам отклоняет операцию еще при ее создании (расширение нового файла сервис-пользователь указывает в параметрах операции), а если это выяснилось только по загруженному файлу - сервис обработки файлов завершает шаг с ошибкой, и операция откатывается;
3) Сервис доступа к файлам отправляет задание на подмену сервису обработки файлов;
4) Сервис обработки файлов берет из операции id подменяемого файла, по индексу находит его текущий путь и путь его json и перемещает оба в корзину операции (trash/<id операции>/). Это первый шаг, и он записывается в операцию. С этого момента прежний файл и прежняя метаинформация сохранены и могут быть возвращены;
5) Сервис обработки файлов перемещает новый файл из временного хранилища на место прежнего, по тому же пути и под тем же именем с тем же расширением. Шаг записывается в операцию;
6) Сервис обработки файлов формирует новый json: раздел "system" с тем же id файла, прежней датой добавления и прежним приславшим сервисом-пользователем, но с новым весом, новым хешем, новой датой изменения и сервисом-пользователем, выполнившим подмену; название, расширение и источник не меняются; раздел "custom" со всеми пространствами и авторство их ключей берутся из прежнего json из корзины, а если в операции передана новая пользовательская метаинформация, она применяется к пространству сервиса-пользователя, выполнившего подмену, как при изменении метаинформации, с обновлением авторства затронутых ключей; чужие пространства подмена не трогает. Json записывается по прежнему пути, шаг записывается в операцию;
7) Сервис обработки файлов обновляет индексную запись файла (размер, хеш, дата изменения, изменивший сервис-пользователь; путь и расширение не меняются), записывает шаг, переводит операцию в "обработана" и сообщает результат;
8) При успехе сервис доступа к файлам завершает операцию, пишет событие "подмена файла" в топик сервиса подписок и отправляет задание на очистку корзины операции. Только после очистки прежний файл исчезает окончательно;
9) При ошибке на любом шаге операция откатывается: новый файл и новый json удаляются, прежний файл и прежний json возвращаются из корзины на свои пути, индексная запись восстанавливается из прежнего json, временный файл удаляется. Файл остается в точности таким, каким был до операции.
Поскольку шаг 4 выполняется до любого уничтожающего действия, в любой момент отката прежние данные есть либо на своем месте, либо в корзине операции, и откат всегда возможен (см. раздел "ОПЕРАЦИИ", корзина операции).
Изменение метаинформации файла также идет через операцию: сервис-пользователь создает операцию в сервисе доступа к файлам, тот передает задание сервису обработки файлов. Прежний json перед изменением также попадает в корзину операции.



УДАЛЕНИЕ ФАЙЛОВ СЕРВИСОМ-ПОЛЬЗОВАТЕЛЕМ ИЗ ФАЙЛОВОГО ХРАНИЛИЩА
Удалить файл может любой зарегистрированный и не заблокированный сервис-пользователь, в том числе файл, загруженный другим сервисом-пользователем (см. раздел "ПОЛИТИКА ДОСТУПА К ФАЙЛАМ").
Общая последовательная схема удаления файла:
1) Сервис-пользователь запрашивает у сервиса доступа к файлам удаление файла или файлов, передавая список их id. Как и при скачивании, в одной операции может быть несколько файлов;
2) Сервис доступа к файлам создает операцию удаления, в которой фиксирует список id файлов, и по каждому файлу проверяет, что он существует и что над ним не идет другая изменяющая операция. Если проверка не прошла хотя бы для одного файла, операция завершается с ошибкой, ни один файл не удаляется, и сервис-пользователь получает ответ с перечнем файлов, по которым проверка не прошла;
3) Если удалить можно, сервис доступа к файлам отдает сервису-пользователю id операции и через кафку передает задание на удаление сервису обработки файлов, указывая id операции. Дальше сервис-пользователь может только запрашивать состояние операции по ее id;
4) Сервис обработки файлов берет список id файлов из операции и по каждому файлу по очереди перемещает файл и его json в корзину операции и удаляет индексную запись файла. Каждый шаг по каждому файлу он фиксирует в операции. Если на каком-то файле произошла ошибка, он останавливается и сообщает об ошибке, не трогая оставшиеся файлы;
5) Сервис обработки файлов через кафку сообщает результат сервису доступа к файлам;
6) При успехе сервис доступа к файлам снимает резервирование имен всех удаленных файлов (имена по этим путям снова свободны), завершает операцию, пишет в топик сервиса подписок по одному событию "удаление файла" на каждый удаленный файл с его метаинформацией на момент удаления и отправляет сервису обработки файлов задание на очистку корзины операции. После очистки файлы не восстановимы;
7) При ошибке операция откатывается по общим правилам: сервис обработки файлов возвращает из корзины на место все файлы и json, которые успел туда переместить, и восстанавливает их индексные записи, сервис доступа к файлам переводит операцию в состояние "откачена". Все файлы из списка остаются в системе, как будто операции не было: частично выполненного удаления не бывает.
Состояние операции удаления сервис-пользователь узнает запросом по id операции. Отдельного подтверждения от него не требуется.



ПОДПИСКА НА ИЗМЕНЕНИЯ В ФАЙЛОВОМ ХРАНИЛИЩЕ
У сервиса-пользователя должна быть возможность подписаться на изменения в файловом хранилище.
Должна быть возможность подписаться на добавление/изменение/удаление файла в файловом хранилище.
Общая схема:
1) Сервис-пользователь через сервис подписок подписывается на определенный вид изменений в файловом хранилище. Подписаться должна быть возможность на добавление файла, перезапись файла, изменение метаинформации файла, удаление файла, возможно ещё что-то. Также должны быть фильтры по сервису-пользователю, который выполнил изменение, по источнику файла, по типу файла(jpg, mp4 и тд), возможно ещё по чему-то. Фильтр по сервису-пользователю задается либо его идентификатором, либо его названием, и это разные подписки с разным поведением: подписка по идентификатору привязана к конкретному сервису-пользователю навсегда, подписка по названию срабатывает на того, кто носит это название в момент изменения, в том числе на нового сервиса-пользователя, занявшего название после отзыва прежнего;
2) После того, как операция успешно завершена, сервис доступа к файлам пишет в топик сервиса подписок сообщение об этом изменении. Изменения, которые были откачены, в топик не попадают;
3) Сервис подписок по подпискам и их фильтрам определяет, каким сервисам-пользователям нужно сообщить об изменении, формирует для них уведомления и пишет их в топик сервиса-нотифайера;
4) Сервис-нотифайер сохраняет уведомления в свою таблицу и отправляет их нужным сервисам-пользователям в их web socket соединения, которые он держит (gateway эти соединения только проксирует). Если доставить уведомление не удалось (сервис-пользователь не подключен или не подтвердил получение), он повторяет отправку согласно политике ретраев, каждый раз увеличивая интервал до следующей попытки в 2 раза;

Уведомление об отзыве регистрации:
Подписки не удаляются системой ни при каких изменениях у других сервисов-пользователей: отписаться может только сам подписчик. Поэтому когда сервис-пользователь отзывает регистрацию (сам или через администратора), все, кто был подписан на его файлы, должны узнать об этом и решить, что делать с подпиской.
1) Сервис авторизации, отозвав регистрацию, сообщает об этом сервису подписок, передавая идентификатор и название отозванного сервиса-пользователя;
2) Сервис подписок удаляет собственные подписки отозванного сервиса-пользователя;
3) Сервис подписок находит все подписки других сервисов-пользователей, у которых фильтр по сервису-пользователю указывает на отозванного: и подписки по его идентификатору, и подписки по его названию;
4) Для каждого такого подписчика сервис подписок формирует одно уведомление типа "сервис-пользователь отозвал регистрацию" и пишет его в топик сервиса-нотифайера. В уведомлении: идентификатор и название отозванного сервиса-пользователя, список id подписок подписчика, которые на него ссылались, и для каждой - по идентификатору она или по названию;
5) Сервис-нотифайер доставляет это уведомление так же, как уведомления об изменениях: с подтверждением и ретраями;
6) Подписки подписчиков система не трогает. Подписка по идентификатору больше никогда не сработает, потому что идентификатор не переиспользуется, и подписчик может ее удалить или оставить. Подписка по названию продолжит действовать и начнет срабатывать на нового сервиса-пользователя, если кто-то займет это название. Если подписчику это не нужно, он должен сам удалить или изменить подписку обычным запросом в сервис подписок.
Уведомления бывают двух типов: об изменении в файловом хранилище и служебные (пока только об отзыве регистрации). Сервис-нотифайер обрабатывает оба типа одинаково, тип указан в уведомлении.



ДОСТАВКА УВЕДОМЛЕНИЙ
Уведомления доставляются сервисам-пользователям по web socket. Соединение всегда инициирует сервис-пользователь, система к сервисам-пользователям сама не подключается: никаких callback-url сервис-пользователь не сообщает и не хранит.
Общая схема:
1) Сервис-пользователь открывает web socket соединение к gateway, предъявив bearer-token. Gateway через ext_authz проверяет токен в сервисе авторизации и, если токен валиден, проксирует соединение в сервис-нотифайер, добавив заголовки с идентификатором сервиса-пользователя и временем протухания токена. Сервис-нотифайер принимает соединение и запоминает, какому сервису-пользователю оно принадлежит. У одного сервиса-пользователя может быть несколько соединений (несколько экземпляров сервиса-пользователя), но не больше 10: лишние сервис-нотифайер закрывает сразу;
2) Соединение живет не дольше bearer-token-а: по времени протухания из заголовка сервис-нотифайер закрывает соединение, сервис-пользователь получает новый токен и переподключается. Если сервис-пользователь заблокирован или отозван, сервис-нотифайер закрывает его соединения по запросу сервиса авторизации;
3) Сервис-нотифайер, получив уведомление, находит открытое соединение этого сервиса-пользователя и отправляет уведомление в него. Если соединений несколько, уведомление отправляется в одно из них;
4) Сервис-пользователь, получив уведомление, отправляет в то же соединение подтверждение с id уведомления. Уведомление считается доставленным только после подтверждения. Если у сервиса-пользователя нет открытого соединения или подтверждение не пришло за отведенное время, доставка считается неудавшейся;
5) Недоставленное уведомление сервис-нотифайер повторяет согласно политике ретраев. Сервис-пользователь должен быть готов получить одно и то же уведомление повторно (если подтверждение потерялось) и отличать повторы по id уведомления.
Через web socket идут только уведомления и подтверждения их получения. Все остальные запросы сервис-пользователь отправляет обычными запросами через gateway.



НАБЛЮДАЕМОСТЬ
Состояние системы отслеживается через логи и метрики, а не через сервис администрирования.
Логи:
1) Каждый внутренний сервис пишет структурированные логи в формате json в stdout, сбор и хранение логов - задача окружения развертывания;
2) В каждой записи лога, относящейся к операции, обязательно указывается id операции, а в записях, относящихся к сервису-пользователю, - его идентификатор. Это позволяет собрать всю историю операции по логам всех сервисов;
3) Уровни: ERROR для ситуаций, требующих вмешательства человека (застрявший откат, уведомление, не доставленное после всех ретраев, ошибка обращения к файловому хранилищу или PostgreSQL), WARNING для подозрительных, но обрабатываемых автоматически (блокировка по подбору секрета, превышение лимитов, откат операции), INFO для нормального хода операций;
4) Секреты, bearer-token-ы и одноразовые токены в логи не попадают никогда;
Метрики:
1) Каждый внутренний сервис отдает метрики на эндпоинте /metrics в формате Prometheus. Как минимум: количество и длительность запросов по эндпоинтам и кодам ответа, количество ошибок;
2) Сервис доступа к файлам: операции по типам и состояниям, длительность операций, количество откатов, количество операций в состоянии "откатывается" и застрявших в откате;
3) Сервис обработки файлов: количество и длительность заданий по типам, ошибки, отставание консьюмера кафки, количество неочищенных корзин операций;
4) Сервис-нотифайер: количество уведомлений по состояниям, количество ретраев, количество уведомлений, не доставленных после всех ретраев;
5) Gateway: стандартные метрики Envoy (запросы по маршрутам и кодам ответа, срабатывания лимитов, отказы ext_authz, объем переданных данных), отдельного кода для них не пишется;
6) Сервис авторизации: выданные токены, неудачные проверки токенов, блокировки по подбору секрета, заявки по состояниям;
7) Сервис-нотифайер дополнительно: количество открытых web socket соединений;
8) Сервис-обертка дополнительно: количество и объем передач файлов, оборванные передачи;
Алерты настраиваются в Grafana. Обязательные: появление операции, застрявшей в откате; уведомление, не доставленное после всех ретраев; блокировка по подбору секрета; рост доли ошибок у любого сервиса; отставание консьюмера кафки; недоступность любого внутреннего сервиса, PostgreSQL или файлового хранилища.

TLS И ЛИМИТЫ GATEWAY
Весь трафик между сервисами-пользователями и системой идет только по TLS: и обычные запросы, и загрузка/скачивание файлов, и web socket соединения. TLS терминирует gateway, незащищенные соединения он не принимает. Сервис администрирования также доступен только по TLS. Внутри закрытой сети между внутренними сервисами TLS не используется (см. раздел "ДОВЕРИЕ МЕЖДУ ВНУТРЕННИМИ СЕРВИСАМИ"). Исключение - файловое хранилище: сервис-обертка обращается к seafile всегда по TLS, независимо от того, где seafile развернут, потому что он может оказаться во внешней сети.
Секрет сервиса-пользователя и bearer-token передаются только в теле запроса или в заголовке Authorization, никогда в url: url попадают в логи.

Gateway (Envoy Gateway) ограничивает частоту запросов средствами Envoy: политиками rate limit на маршрутах. Лимиты считаются по алгоритму token bucket, при превышении gateway отвечает 429 с заголовком Retry-After и запрос дальше не пропускает. Для маршрутов без токена лимит считается по адресу отправителя и применяется до любых обращений во внутренние сервисы. Для маршрутов с токеном лимит считается по идентификатору сервиса-пользователя из заголовка, который проставил сервис авторизации при проверке токена (ext_authz в Envoy выполняется раньше rate limit, поэтому заголовок к этому моменту уже есть).
Запросы без токена, по адресу отправителя:
1) Подача заявки на регистрацию: 5 в час с одного адреса;
2) Запрос статуса заявки: 30 в минуту с одного адреса;
3) Запрос bearer-token-а: 10 в минуту с одного адреса. Защита от подбора секрета по идентификатору сервиса-пользователя (блокировка после 10 неудачных попыток подряд) в gateway не реализуема и живет в сервисе авторизации (см. раздел "АВТОРИЗАЦИЯ");
Запросы с токеном, по идентификатору сервиса-пользователя:
4) Обычные запросы (операции, метаинформация, подписки): 600 в минуту, burst до 100;
5) Web socket: не более 1 нового соединения в секунду. Лимит на количество открытых соединений (не более 10 на сервис-пользователя) gateway посчитать не может, его держит сервис-нотифайер;
Лимиты, которые gateway посчитать не может, потому что не знает состояния системы, держат внутренние сервисы:
6) Загрузка и скачивание файлов: не более 10 одновременных передач на сервис-пользователя. Проверяет сервис доступа к файлам при проверке одноразового токена, по числу своих токенов, передача по которым идет прямо сейчас. Лимита на количество передач нет, так как каждая передача уже привязана к одноразовому токену и операции;
Все значения лимитов задаются конфигурацией (gateway или соответствующего сервиса) и могут быть изменены без изменения кода.

Размер тела запроса:
1) Обычные запросы (создание операции, метаинформация, подписки): 1 МБ, ограничивает gateway. Этого достаточно для любой пользовательской метаинформации, более крупную метаинформацию нужно хранить как отдельный файл;
2) Загрузка файла: 20 ГБ на один файл. Тело файла gateway не буферизует, а проксирует потоком, поэтому лимит проверяется в два приема: по заголовку Content-Length его проверяет сервис доступа к файлам при проверке одноразового токена, а по фактически переданному объему во время передачи - сервис-обертка, которая при превышении разрывает соединение, удаляет временный файл и сообщает сервису доступа к файлам об обрыве, после чего операция откатывается;
3) Сообщение в web socket от сервиса-пользователя (подтверждение получения): 4 КБ, ограничивает сервис-нотифайер;
Таймаут на бездействие при загрузке и скачивании файла: 60 секунд без передачи данных, держит gateway (stream idle timeout в Envoy), после чего соединение разрывается, сервис-обертка видит обрыв и сообщает о нем сервису доступа к файлам, а операция загрузки откатывается.

ДОВЕРИЕ МЕЖДУ ВНУТРЕННИМИ СЕРВИСАМИ
Пока что авторизации между внутренними сервисами нет. Все внутренние сервисы (gateway, сервис авторизации, сервис доступа к файлам, сервис обработки файлов, сервис подписок, сервис-нотифайер, сервис администрирования, сервис-обертка, Prometheus, Grafana) считаются доверенными: любой из них может обратиться к любому другому внутреннему сервису, а через сервис-обертку - к любым данным в PostgreSQL и файловом хранилище. Ни сервис-обертка, ни другие внутренние сервисы не проверяют, кто к ним обращается.
Единственная граница доверия проходит между сервисами-пользователями и системой: ее держит gateway через проверку bearer-token в сервисе авторизации и проверку одноразовых токенов в сервисе доступа к файлам (ext_authz). Заголовки с идентификатором сервиса-пользователя, id операции и путем, которые gateway добавляет к запросу по результату этих проверок, внутренние сервисы принимают на веру: подделать их снаружи нельзя, потому что gateway удаляет одноименные заголовки из входящего запроса, а внутрь закрытой сети снаружи доступа нет. Поэтому ни один внутренний сервис, кроме gateway, не должен быть доступен из внешней сети: внутренние сервисы, PostgreSQL и Kafka живут в закрытой сети, наружу публикуется только gateway. Сервис администрирования доступен только администратору из этой же закрытой сети.
Файловое хранилище (seafile) - исключение: оно не обязательно находится в закрытой сети и может быть доступно из внешней. Поэтому доверие к нему не сетевое, а по учетным данным: сервис-обертка ходит в seafile по TLS с отдельной учетной записью seafile, эта учетная запись хранится только в Secret сервиса-обертки и больше нигде, а внутри seafile ей принадлежат только библиотеки системы. Никто другой в системе учетных данных seafile не знает, и ни один сервис, кроме сервиса-обертки, к seafile не обращается. Если seafile доступен из внешней сети, его собственная защита (учетные записи, TLS, лимиты) - зона ответственности seafile и его развертывания, а не этой системы.
Авторизация между внутренними сервисами (mTLS или сервисные токены) возможно будет добавлена позже.

ПОЛИТИКА ДОСТУПА К ФАЙЛАМ
Пока что никакой политики доступа к файлам нет. Любой зарегистрированный и не заблокированный сервис-пользователь может загружать файлы, скачивать любые файлы, подменять любые файлы, удалять любые файлы и изменять метаинформацию любых файлов, в том числе загруженных другими сервисами-пользователями.
Проверка "можно ли выполнить действие" в сервисе доступа к файлам сводится к техническим условиям: сервис-пользователь прошел проверку bearer-token, файл существует (для скачивания, подмены, удаления и изменения метаинформации), над файлом не идет другая изменяющая операция (для подмены, удаления и изменения метаинформации), имя файла не занято (для загрузки с сохранением имени), пользовательская метаинформация является валидным json-объектом.
Политика доступа (владелец файла, роли, ACL) возможно будет добавлена позже. Чтобы это было безболезненно, проверка должна быть вынесена в отдельный модуль сервиса доступа к файлам с единым интерфейсом, который сейчас всегда разрешает действие, а в метаинформации файла уже сейчас должен сохраняться сервис-пользователь, который его загрузил.

ОБЩИЕ ПОЛОЖЕНИЯ СИСТЕМЫ
Все собственные сервисы системы (сервис авторизации, сервис доступа к файлам, сервис обработки файлов, сервис подписок, сервис-нотифайер, backend сервиса администрирования, сервис-обертка) пишутся на python, сетевой слой каждого - FastAPI. Исключения два: gateway - это Envoy Gateway, у него нет своего кода, только конфигурация; веб-интерфейс сервиса администрирования - React. Других языков и веб-фреймворков нет.
Разворачивание системы идет через Kubernetes. Все компоненты (собственные сервисы, gateway, Kafka, PostgreSQL, Prometheus, Grafana, сервис администрирования) разворачиваются в одном кластере Kubernetes; файловое хранилище (seafile) может жить где угодно: внутри кластера, снаружи в закрытой сети или вообще во внешней сети. К нему обращается только сервис-обертка, и обращается так, как если бы оно всегда было во внешней сети: по TLS и с учетными данными seafile, которые есть только у сервиса-обертки (см. раздел "ДОВЕРИЕ МЕЖДУ ВНУТРЕННИМИ СЕРВИСАМИ"). Каждый собственный сервис собирается в docker-образ и описывается манифестами Kubernetes, которые хранятся в репозитории рядом с кодом. Конфигурация gateway (Gateway API и ресурсы Envoy Gateway) - такие же манифесты в том же репозитории. Закрытая сеть из раздела "ДОВЕРИЕ МЕЖДУ ВНУТРЕННИМИ СЕРВИСАМИ" - это сеть кластера: наружу через Gateway публикуется только gateway, остальные сервисы доступны только внутри кластера. Все настройки сервисов (адреса соседей, лимиты, таймауты, учетные данные) задаются через ConfigMap и Secret, а не зашиваются в образ. Локальная разработка и отладка не требуют Kubernetes: каждый сервис должен запускаться как обычное python-приложение с настройками из переменных окружения.
Каждое взаимодействие сервиса-пользователя с файловым хранилищем (загрузка, скачивание, подмена, удаление, изменение метаинформации, запрос метаинформации, запрос списка источников) должно логироваться в postgres. Для этого используются операции: взаимодействия с файловым хранилищем вне операции не существует (см. раздел "ОПЕРАЦИИ").
Код должен писаться в полном соответствии принципам ООП и SOLID.
Работа с PosgreSQL должна идти через ORM. На каждую сущность в Postgres должно быть 3 сущности: DTO класс, ORM класс и класс-маппер одного в другое.
