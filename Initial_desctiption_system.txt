СИСТЕМА ДЛЯ СОХРАНЕНИЯ ВСЕГО ЧЕГО МОЖНО В ЦЕНТРАЛИЗОВАННОМ ВИДЕ



ИДЕЯ:
Идея в том, чтобы автоматически сохранять медиа информацию из разных источников(телеграмм, телефон и тд) в централизованное хранилище.



МИКРОСЕРВИСЫ, ИЗ КОТОРЫХ СОСТОИТ ПРОЕКТ:
1) Основное файловое хранилище.
Хранение файлов будет осуществляться в seafile, однако код должен поддерживать безболезненный переезд на любое другое файловое хранилище(взаимодействие с файловым хранилищем должно идти строго через наш интерфейс).
Файловое хранилище должно хранить всю информацию, необходимаю для работы системы и для сохранения целостности и консистентности данных.
С основным файловым хранилищем взаимодействие идет только через сервис-обертку. Никто больше не имеет прямого доступа к основному файловому хранилищу.

2) База данных.
Хранение информации, необходимой для работы проекта, но не связанной напрямую с самими файлами должно осуществляться в PostgreSQL.
С базой данных взаимодействие идет только через сервис-обертку. Никто больше не имеет прямого доступа к базе знаний.

3) Сервис-обертка над базой знаний.
Сервис должен быть оберткой над базой знаний.
Написан должен быть на python. Взаимодействие с PostgreSQL должно осуществляться через SQLAlchemy.
Для работы с сетью должен выступать FastAPI.

4) Сервис обработки файлов.
Воркер, который обрабатывает файлы внутри системы. С сервисами-пользователями он не взаимодействует и запросов от них не получает.
Задания на обработку он получает через кафку от сервиса доступа к файлам. Получив задание о загруженном файле, он обрабатывает файл, если необходимо, перемещает его из места временного хранения в нужную директорию и создает файл с метаинформацией о нем. При подмене файла в задании приходит id файла, который нужно подменить. Изменение метаинформации файла также выполняет он по заданию.
С файловым хранилищем и базой данных работает через сервис-обертку. После каждого изменения в файловом хранилище пишет сообщение об этом в топик сервиса подписок.
Написан должен быть на python.

5) Сервис авторизации.
Отвечает за регистрацию сервисов-пользователей, выдачу bearer-token-ов и их проверку. Сервис обработки файлов этой логикой не занимается.
Данные о зарегистрированных сервисах-пользователях хранит в PostgreSQL через сервис-обертку.
Написан должен быть на python.

6) Сервис доступа к файлам.
Все взаимодействие сервисов-пользователей с файлами идет через него: запросы на загрузку, подмену и скачивание файла, сообщения о загруженных файлах, запросы и изменение метаинформации gateway направляет в сервис доступа к файлам.
Проверяет можно ли сервису-пользователю выполнить запрошенное действие с файлом и выдает одноразовые токены с ttl на загрузку и скачивание файлов.
Метаинформацию о файлах по запросу сервиса-пользователя отдает он же.
Сам файлы он не обрабатывает: задания на обработку загруженного файла, подмену файла и изменение метаинформации он через кафку передает сервису обработки файлов.
Если действие разрешено, сервис доступа к файлам фиксирует состояние файла (резервирует в postgres имя файла) и выдает одноразовый токен.
Одноразовый токен проверяет тот же сервис, который его выдает: gateway, получив от сервиса-пользователя запрос на загрузку или скачивание файла, делает запрос на сервис доступа к файлам для проверки одноразового токена и только после этого пропускает запрос в сервис-обертку.
Данные хранит в PostgreSQL через сервис-обертку.
Написан должен быть на python.

7) Сервис подписок.
Используется для реализации подписок на изменения в файловом хранилище.
Принимает подписки от сервисов-пользователей, получает события об изменениях в файловом хранилище, формирует уведомления для подписанных сервисов-пользователей и через кафку отправляет их в сервис-нотифайер.

8) Сервис-нотифайер.
Занимается только отправкой уведомлений сервисам-пользователям. Уведомления получает через кафку от сервиса подписок и отправляет их сервисам-пользователям через gateway.
В сервисе-нотифайере должна быть таблица с уведомлениями и политикой ретраев.
Политика ретраев должна быть экспоненциально затухающей: каждый следующий ретрай выполняется через в 2 раза большее время, чем предыдущий.

9) Kafka.
Кафка используется только для взаимодействия между внутренними сервисами системы. Сервисы-пользователи с кафкой не взаимодействуют: все свои запросы они отправляют через gateway.
Через кафку сервис доступа к файлам передает задания сервису обработки файлов, сервис обработки файлов передает события об изменениях сервису подписок, а сервис подписок передает уведомления сервису-нотифайеру.

10) Gateway.
Единая точка входа для сервисов-пользователей. Сервис-пользователь не обращается к внутренним сервисам напрямую: все его запросы приходят в gateway, который перенаправляет их в нужный сервис (сервис авторизации, сервис доступа к файлам, сервис подписок, сервис-обертку). Одноразовые токены на загрузку и скачивание файлов gateway проверяет запросом в сервис доступа к файлам.
В обратную сторону то же самое: уведомления от сервиса-нотифайера идут сервисам-пользователям через gateway.
Когда я пишу, что сервис-пользователь обращается к какому-то внутреннему сервису, подразумевается, что он делает это через gateway.
Сам gateway bearer-token не проверяет: на каждый запрос сервиса-пользователя он делает запрос в сервис авторизации, и тот проверяет токен. Запросы, токен которых сервис авторизации не подтвердил, gateway дальше не пропускает. Исключение - регистрация и запрос bearer-token-а.

11) Множество регистрируемых сервисов-пользователей.
Сервисы-пользователи должны регистрироваться в системе, сообщать ей информацию о пользователе, после чего в своем life circle отправлять медиа в систему и/или получать медиа из нее.
Написаны могут быть на чем угодно.



АВТОРИЗАЦИЯ:
За авторизацию отвечает отдельный сервис авторизации.
Регистрацию-рукопожатие должен инициировать сервис-пользователь, обращаясь к сервису авторизации.
Во время рукопожатия сервис-пользователь должен передавать свое название и мастер-ключ. Сервис-пользователь, не знающий мастер-ключ не может зарегистрироваться.
В ответ сервис авторизации должен отправлять уникальный идентификатор, связанный с этим сервисом-пользователем.
Дальше сервис-пользователь должен запросить bearer-token у сервиса авторизации, передав свой идентификатор и мастер-ключ. После протухания сервис-пользователь должен перезапрашивать bearer-token.
Проверяет bearer-token тот же сервис, который его выдает, - сервис авторизации. Gateway, получив запрос от сервиса-пользователя, делает запрос на сервис авторизации для проверки токена. Внутренние сервисы получают уже проверенные запросы.
Одноразовые токены на загрузку и скачивание файлов к сервису авторизации не относятся: их выдает и проверяет сервис доступа к файлам.



ОТПРАВКА ФАЙЛОВ СЕРВИСОМ-ПОЛЬЗОВАТЕЛЕМ В ФАЙЛОВОЕ ХРАНИЛИЩЕ:
Обшая последовательная схема:
Когда я пишу, что какой-то сервис пишет файл в файловое хранилище, подразумевается, что он делает это через сервис-обертку этого файлового хранилища.
1) Сервис-пользователь, согласно своей внутренней логике, получает файл, который нужно сохранить в файловое хранилище;
2) Сервис-пользователь отправляет всю метаинформацию, касающуюся файла, запросом в сервис доступа к файлам;
3) Сервис доступа к файлам получает метаинформацию и проверяет можно ли загрузить файл в файловое хранилище;
4) Если загрузить файл нельзя, то сервис доступа к файлам сообщает об этом сервису-пользователю в ответе на запрос;
5) Если загрузить файл можно, то сервис доступа к файлам фиксирует состояние этого файла, чтобы никто другой не мог каким-то образом помешать дальнейшей загрузке файла в файловое хранилище(резервирует в postgres имя файла, чтобы другой сервис-пользователь не мог его занять). После отдает сервису-пользователю в ответе на запрос одноразовый токен с ttl и путь, по которому файл необходимо загрузить. Этот токен должен давать возможность загрузить файл только по требуемому пути;
6) Сервис-пользователь при помощи этого одноразового токена (его проверяет сервис доступа к файлам) через сервис-обертку базы знаний сохраняет файл в файловое хранилище в место, отведенное под временное хранение файлов(в seafile это директория специальная, в S3 это будет просто специальный подпуть);
7) Сервис-пользователь запросом в сервис доступа к файлам сообщает ему id или путь файла в файловом хранилище, метаинформацию по файлу и всю прочую требуемую информацию;
8) Сервис доступа к файлам через кафку передает задание на обработку файла сервису обработки файлов;
9) Сервис обработки файлов обрабатывает файл, если необходимо, перемещает его в нужную директорию, а также создает файл с метаинформацией о файле;

Когда сервис-пользователь отправляет медиа он должен также отправлять информацию об источнике этой медиа. Источник может быть вложенным. Передавать необходимо списком, где каждый следующий элемент это подкаталог. Файлы в файловом хранилище должны группироваться соответственно источнику. Если источник вложенный, то должно формироваться дерево каталогов.

Вместе с самим файлом в файловое хранилище должен сохраняться json файл с метаинформацией о нем.
Этот json файл необходимо сохранять по тому же пути, но в другую директорию на верхнем уровне.
Например если файл сохранен по пути "<путь_к_корневой_директории_проекта>/file_storage/youtube/channel_name/video_1.mp4", то json файл с метаинформацией должен быть сохранен в "<путь_к_корневой_директории_проекта>/metadata/youtube/channel_name/video_1.json"
Сервис обработки файлов должен сохранять туда:
1) Уникальный id файла(UUID);
2) Название файла;
3) Расширение файла;
4) Вес файла;
5) Дату и время добавления файла;
6) Сервис-пользователь, приславший файл;
7) Источник, откуда сервис-пользователь взял файл;
8) Возможно ещё какие-то поля;

Сервис-пользователь при отправке файла должен иметь возможность добавить свою метаинформацию о файле. Подаваться должно в формате json, который будет 1 в 1 добавлен к метаинформации о файле. В случае коллизий имен с системными ключами необходимо не сохранить файл и сообщить об этом сервису-пользователю.

Сервис-пользователь при отправке файла должен указывать нужно ли сохранять имя файла или нет. Если имя сохранять не нужно, то сервис обработки файлов должен переименовать файл при помощи UUID. Если имя нужно сохранять, но в файловом хранилище файл с таким именем по такому пути уже существует, то необходимо не сохранять файл и сообщить об этом сервису-пользователю.



ПОЛУЧЕНИЕ ФАЙЛОВ СЕРВИСОМ-ПОЛЬЗОВАТЕЛЕМ ОТ ФАЙЛОВОГО ХРАНИЛИЩА
Должно быть 2 пути:
1) Запрос метаинформации по файлу/файлам;
2) Запрос самого файла;

Общая последовательная схема запроса метаинформации по файлу/файлам:
1) Сервис-пользователь запрашивает у сервиса доступа к файлам метаинформацию по id файла/файлов или фильтрам;
2) Сервис доступа к файлам отправляет в ответе на запрос всю метаинформацию по запрашиваемому файлу/файлам;

Общая последовательная схема запроса файла/файлов:
Когда я пишу, что какой-то сервис пишет файл в файловое хранилище, подразумевается, что он делает это через сервис-обертку этого файлового хранилища.
1) Сервис-пользователь запрашивает у сервиса доступа к файлам файл/файлы по его/их id;
2) Сервис доступа к файлам проверяет можно ли сервису-пользователю скачать файл/файлы. Если можно, то в ответе на запрос дает сервису-пользователю одноразовый токен с ttl на каждый запрашиваемый файл и url/url-ы, по которому надо скачать файл/файлы. Токен должен позволять скачать файл только по конкретному пути;
3) Сервис-пользователь при помощи одноразового токена/токенов (их проверяет сервис доступа к файлам) через сервис-обертку файлового хранилища скачивает требуемые файлы;

Должны быть фильтры:
1) По сервису-пользователю, который добавил/изменил файл;
2) По источнику файла(если у указанного источника есть подисточники, то возвращать нужно рекурсивно все файлы из подисточников);
2) По типу файла (png, mp4, pdf и т.д.);
3) Возможно ещё какие-то фильтры;



РЕДАКТИРОВАНИЕ ФАЙЛОВ СЕРВИСОМ-ПОЛЬЗОВАТЕЛЕМ В ФАЙЛОВОМ ХРАНИЛИЩЕ:
Сервис-пользователь должен иметь возможность редактировать файлы, уже загруженные на файловый сервер.
Должна быть возможность:
1) Подменить сам файл;
2) Добавить поля с метаинформацией;
3) Обновить существующие поля с метаинформацией;
4) Возможно ещё что-то;

Общая последовательная схема подмены файла такая же, что и при загрузке файла, но файл должен не просто загружаться, а подменять существующий, id которого сервис-пользователь сообщил сервису доступа к файлам. Сервис доступа к файлам передает этот id сервису обработки файлов в задании на обработку.



ПОДПИСКА НА ИЗМЕНЕНИЯ В ФАЙЛОВОМ ХРАНИЛИЩЕ
У сервиса-пользователя должна быть возможность подписаться на изменения в файловом хранилище.
Должна быть возможность подписаться на добавление/изменение файла в файловом хранилище.
Общая схема:
1) Сервис-пользователь через сервис подписок подписывается на определенный вид изменений в файловом хранилище. Подписаться должна быть возможность на добавление файла, перезапись файла, изменение метаинформации файла, возможно ещё что-то. Также должны быть фильтры по сервису-пользователю, который добавил файл, по источнику файла, по типу файла(jpg, mp4 и тд), возможно ещё по чему-то;
2) После того, как сервис обработки файлов внес изменение в файловое хранилище он пишет в топик сервиса подписок сообщение об этом изменении;
3) Сервис подписок по подпискам и их фильтрам определяет, каким сервисам-пользователям нужно сообщить об изменении, формирует для них уведомления и пишет их в топик сервиса-нотифайера;
4) Сервис-нотифайер сохраняет уведомления в свою таблицу и через gateway отправляет их нужным сервисам-пользователям. Если отправить уведомление не удалось, он повторяет отправку согласно политике ретраев, каждый раз увеличивая интервал до следующей попытки в 2 раза;



ОБЩИЕ ПОЛОЖЕНИЯ СИСТЕМЫ
Каждый запрос на загрузку, скачивание, изменение и тд файлов должен логироваться в postgres.
Код должен писаться в полном соответствии принципам ООП и SOLID.
Работа с PosgreSQL должна идти через ORM. На каждую сущность в Postgres должно быть 3 сущности: DTO класс, ORM класс и класс-маппер одного в другое.
